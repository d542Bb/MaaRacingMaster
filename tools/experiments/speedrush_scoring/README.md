# speedrush 记分观测与规则实测（C 类实验，2026-09-17）

> **本文是什么**：驾驶页 HUD 的读数链路、**每格 ROI 的复核结论**与**记分规则实测结论**——各加分项折算多少分、分数以什么形态出现、能否从录制数据事后复算。
> **本文不是什么**：不是游戏规则的真源（外部事实归 [`RULES.md`](../../../maaracing_master/plugins/speedrush/RULES.md)，本文只提供实测证据供其回填复核）；不是控制方案（见本机 `docs/plan/speedrush-control-route.md`）。
> **信源等级**：L4（过程与证据）—— 可作「这个事实当时怎么验的、结论与复现命令」的依据；结论经维护者复核回填 `RULES.md` 后才升为 L0。
> **继承**：实验规范见 [`tools/experiments/README.md`](../README.md)（C 类两条硬约束、资产分界、目录约定）。

回答的问题：**「极速狂飙」驾驶阶段的分数是怎么来的**——各加分项折算多少分、分数在画面上
以什么形态出现、能否从录制数据里事后复算。这是「胡萝卜模型」（决策层收益模型）的输入规格：
规则没测清之前设计收益模型，等于拿印象当系数。

## 方法与判据

- **素材**：`data/speedrush/demos/` 下的已录会话（一轮两阶段各一段，1280×720）。录制帧含完整
  HUD，故**规则实测不必等新实机**——离线即可读数。
- **读数链路**：`probe_hud_ocr.py`。标定用 `discover`/`scan`（带文本检测，先定位再定 ROI），
  生产口径用 `read`/`timeline`/`formula`（关文本检测，与 treasure OCR 同口径：固定 HUD
  文字框下 det 是冗余计算）。**复盘链路**：`review_run.py`——实时读数落地后，「分从哪来」
  从落盘的 `hud.jsonl` 复算，不再重跑 OCR（同一帧识别两次会给出两个答案）。
- **ROI 真源**：`maaracing_master/plugins/speedrush/resources/policy/hud_regions.json`
  （2026-09-17 实时读数落地后由本目录搬进插件；插件侧 `hud.py` 与探针读**同一份**，探针
  `--rects` 缺省即指向它）。`scan` 的**按位置统计**只负责给候选，**每一格都必须过
  下面的复核**才留下——本轮复核推翻了三个候选（见「复核结论」），说明"扫出来"不等于"压对了"。
- **面板在场闸门**：`field_on_dark()`。左侧卡片会周期性出现、出现时**先淡入**（半透明、
  数字滚动、合计行未显），直接对 ROI 做 OCR 会读到天空、产出垃圾值。判据是 ROI 内暗像素
  占比（纯 numpy，零 OCR 开销）；后续又加了"定值"这道时间维判据（见复盘工具一节）。
- **标尺独立性**：读数来自画面（PIL 读盘 → RapidOCR），与"策略应当怎样"无关。但**同一条链路
  内部的多字段互证不算独立标尺**（它只证明仪器自洽）——语义结论的独立标尺是**人眼看帧**；
  判据与纪律见 [`plugins/speedrush/CODE_WIKI.md` §5](../../../maaracing_master/plugins/speedrush/CODE_WIKI.md)
  的「读数结论的标尺与纪律」（那里的第 1 条就是从本目录这轮返工里立起来的）。

## 复核判据：本轮踩出来的四个坑

复核 ROI 时，"读到字了"和"没读到字"**都不能单独当证据**——两头都会骗人：

1. **框里没东西时 rec 也会强行解码**。关 det 的 rec 被强制出一行文本，于是护栏的水平高光
   读成 `-`、车尾贴纸读成 `TXT`/`VNI`/`甲`、树叶读成 `D`。判"真读到东西"必须要求
   **中文/字母/数字**（正则 `[\u4e00-\u9fff\dA-Za-z]`），不能只判"非空"。
   实测代价：据此选出过"事件横幅场景"帧，框里其实是护栏。
2. **暗底闸门会被深色景物骗过**。面板闸门（暗像素占比）在棕榈树上是达标的。故面板在场
   判据必须是「闸门 **且** 三个字段都读出数字」。
3. **det 对小型 HUD 文字会失明，但这不是 ROI 错**。左侧面板三格在同一帧上 det 报"0 块"，
   而 rec 三个数全读对——det 视角的"框内无字"与"框压错了"是两回事，别据 `dump` 单独定罪。
4. **偶发元素不能先猜框再验证**。浮字跟着车在屏幕上跑（实测 `+30`/`+120` 横跨
   x 0.38–0.59、y 0.44–0.70），固定 ROI 只能偶尔撞上。正确顺序是**先扩大窗口用 `find`
   找真实文字块**，由命中坐标给出该元素在哪，再决定要不要定框——甚至决定它根本不该定框。
5. **"读数对"不等于"语义对"**。左侧面板三格每一格都读对了（与画面数字逐一相符），但我据
   "看起来单调递增"把它判成"本阶段累计里程"——**读数正确、解释错误**。判语义必须用
   "它该不该单调、该不该重置"这类**跨帧性质**去验，不能只看单帧读没读对。
   本轮据此撤回了"里程是累计里程"与"里程+超车占约一成二"两条结论（见结论 2/3）。
   这条已经不留在本目录：**正本升格到域文档**（[`plugins/speedrush/CODE_WIKI.md` §5](../../../maaracing_master/plugins/speedrush/CODE_WIKI.md)
   的「读数结论的标尺与纪律」，三条常驻判据），此处保留的是当时的现场证据与代价。
6. **暗底闸门会漏，且没有可靠的二次在场判据**。面板不在场时，暗色景物（建筑、车辆）能满足
   "暗像素占比"而骗过闸门，识别模型再把它强行解码成单个数字——本轮据此产出过一次假读
   （帧 365 "里程=2"，看着像"重置到 0"，目视核对发现面板整个不在场）。
   **试过用"标签在场"做二次判据，不可行**：取 `里程`/`超车` 两个标签位做 ROI，31 个采样帧
   **零命中**（读出来是 `用`、`一田` 这类碎片——标签字太小）。因此离线稀疏采样下，
   "面板在场读出一个小数字"与"面板缺席读出噪声"**无法从单帧区分**。
   消费方（实时读数）应以**时间连续性**为二次判据（段内里程单调），而不是只看单帧——
   这是把这条坑真正修掉的位置。

### 另一处复核发现：两块比分面板**会上下互换**

右上两块比分面板（本机玩家=蓝底、对手=红底）**不是固定上下**。按"带内饱和像素均色"逐帧判定，
一段之内互换多次、每次互换后各稳定一段：

| 帧区间 | 上块 | 下块 |
|---|---|---|
| 25–43 | 本机(蓝) | 对手(红) |
| 49–85 | 对手(红) | 本机(蓝) |
| 91–391 | 本机(蓝) | 对手(红) |
| 397–565 | 对手(红) | 本机(蓝) |

触发条件未知（得分反超？事件？动画？），已记入缺口表。**后果**：任何按"上／下"判定敌我的读数
都不可信——这正是原 `score_self`/`score_opp` 命名埋的坑（本轮据此产出过一条无效结论）。
判定敌我必须按**块的颜色**：探针的 `block_side()` 取该带内**饱和像素**均色，而不是固定采样点
——固定点会被天空骗过（实测：天空同样满足 B>R，于是判出"下方永远是我方"这种假结论）。

`overlay` 出的图里每格比分都会标出当前归属，可直接看图核。

### 换位时的**几何**：两卡版式不同，同槽位内两卡的带并不重合（2026-09-18 实测）

用检测框逐帧量了两态四个组合的**数值带**（像素 y，1280×720；本机卡多一行「得分速度」、
比分字号更大，对手卡没有速度行）：

| 位置 | 卡片 | 得分速度 | 比分 | 昵称 | 血量 |
|---|---|---|---|---|---|
| 上档 | 本机(蓝) | 31–53 | 49–93 | 69–93 | 89–109 |
| 下档 | 本机(蓝) | 119–141 | 139–180 | 158–178 | 174–196 |
| 上档 | 对手(红) | 无此行 | 50–88 | 64–88 | 82–98 |
| 下档 | 对手(红) | 无此行 | 142–172 | 150–174 | 170–184 |

- **同一张卡在两态只差一个整体平移**（实测位移 ≈ 87–92 px），跨会话同态数值一致——即卡片
  尺寸恒定，没有缩放。
- 但**两卡版式不同**：比分右缘本机约在 x 1135、对手约在 x 1161（同槽位横向差可达 ~54 px），
  字号也不同（本机大、对手小）。
- 故**"一个槽位一个框"只是靠框够大在兜**：实测纵向余量只剩 2–4 px，对手比分右缘正好压在
  框边（而其昵称从 x 1153 就开始了）。**精确解是按 (色 × 位) 分框**——比分 4 个、速度 2 个
  （对手没有速度行）。上面这张表是测量记录与取舍依据；框的最终取值**只在真源**
  （`plugins/speedrush/resources/policy/hud_regions.json`）里，不在此处复写。

复现：对 `20260917_220706_p1`（一场内含两态）与另两场各取一帧，跑检测框并打印 x>0.70W 的
文本盒即可（本表就是那条命令的输出，非目测）。

## 结论

### 1. 合计分值 = 里程 + 30 × 超车 `[实测]`

同帧三个字段同时可读时，逐点比对（`formula` 模式，跨会话）：

| 超车 | 合计 − 里程 |
|---|---|
| 0 | **0** |
| 1 | **30** |
| 3 | **90** |
| 4 | **120** |
| 5 | **150** |

五个档位、两个阶段独立吻合；并与 `RULES.md` §7#4 已记录的观测「里程 338 + 超车 1 → 合计 368」
一致。**另有独立旁证**：画面上的 `+30` 浮字反复出现（见结论 6），与系数 30 同源。

⚠ **少数采样点上公式不成立，但那是假读而非例外**：`合计` 那一格在**卡片淡入完成前**不存在
（该处仍是暗底，闸门拦不住），识别会强行解码出 `92`、`1` 这类小数字，于是出现「合计 < 里程」。
`formula` 模式会把这些点单独列出来（实测 84 个采样点里 4 例，且**全部出现在阶段 2**）。
**由公式自身导出的过滤器**：合计 = 里程 + 30×超车 ≥ 里程，所以「合计 < 里程」必是假读——
消费方按这条过滤，不要信单帧的合计。实时读数落地后，这条过滤器已写进
`plugins/speedrush/hud.py`（`total_left` 单字读数 → 行内 `flags`），复盘侧的对应判据是
`review_run.py` 的「定值」与「公式」两列：**只有定值点参与公式检验**（见结论 2）。

### 2. 左侧卡片是**周期刷新的窗口小结**：里程 = 该窗口的里程，不是跨窗累计 `[实测]`

**本条改过两次，现在定案。** 轨迹：① 最初记为"累计里程、段内单调" → ② 发现"段内单调、
跨段换量级"后撤回，留下 H1（本段累计）与 H2（滚动窗口）两假说并存 → ③ 实时连续读数
（`hud.jsonl`）+ 复盘工具（`review_run.py`）把两假说分开：**H2 成立，H1 被反证**。

判据三条，逐条可复跑（`review_run.py windows`，图见 `sheet`）：

- **出现节奏是固定时钟**：每段出现 4 次，相邻两次的起始时刻差 9.2–10.0 秒（中位 9.9，n=6），
  每次在场约 3.0 秒（2.95–3.58）。"本段小结"不该由固定时钟决定出现时刻；固定周期说明它是
  **时间驱动的周期小结**。
- **跨窗量级不增**：四个窗的里程定值落在 338–344（一段内 338/338/342，另一段 341/341/341/344）。
  若为"跨窗累计"，后一窗必须显著大于前一窗；实测同量级。
- **窗内定值满足合计公式**：三格都定值的采样点上，`合计 = 里程 + 30×超车` **全部成立**
  （0 违例——`check` 模式的公式列）。故「合计」也是**本窗口**的小结分。

早先的两条判读据此纠正：

- **"矮版变体"是误读**：那不是变体，是**同一张卡片淡入中**——半透明、数字还在滚动、
  「合计」那一行还没显出来。`sheet` 出的图一眼可辨：爬升行的面板半透明且只有两格，
  定值行实心且三行齐。量化辅助判据（暗底占比：实心 0.81–0.94、淡入 0.53–0.63）保留备查。
- **"堵车导致不涨"这个混淆项已死**：平台期不是"涨不上去"，而是**滚动动画已收敛的定值**，
  与前方是否被堵无关。故不再需要"前沿车流拖慢里程"的解释，也不再需要"段边界"这个假设。

顶部那条亮条仍**不是**判据（各帧长度完全相同，是静态亮条）。

**旧素材里的 272/278 量级读数不必用"另一段"解释**：窗口量随车速变（10 秒里跑多远就是多少），
更早那两场录像未带实时读数，无法判那些读数是"另一速度下的窗口定值"还是"爬升值"——两种解释
都不需要「段」。要判需带实时读数的连续数据（现在有了：再录一轮即可）。

### 3. ~~里程 + 超车 只占总分的一小部分~~ —— **该条撤回，占比无法由左侧面板得出** `[已撤回]`

原先的算法是「同帧 左侧合计 ÷ 右上总分」（得出一成二之类）。但结论 2 已证左侧合计是**会重置的
计数**，拿它当"本阶段累计的里程+超车得分"去和累计总分相除，**分母与分子不是同期的量**，
比例没有意义。

仍然成立的是：**右上总分在阶段内涨到数千**（实测到 3693），而左侧滚动计数在几百量级——这说明
累计总分里**绝大部分不来自左侧那两项**，与 `RULES.md` §4.2 的「主要加分项＝金币」`[权威]`
方向一致。但**"占多少百分比"这句话本实验给不出**，需先测清左侧计数的口径，或改用
分数增量的来源归因（见缺口表）。

**替代方案"增量归因"试过、离线走不通。** 做法是用 `find` 的检测引擎在路面带内搜浮字、把每个
`Δ总分 ≥ 90` 的时刻与**同时刻**的超车增量、横幅档位、浮字对齐。结果：① 带内检测会把车牌、
`N米` 距离标注、HUD 数值一并捞进来，**浮字与噪声不可分**（同一帧同时报 `+120` 与 `0000`、`12米`）；
② 比分面板会上下互换，4 帧间隔的稀疏采样一遇互换就断链，`Δ` 大量取不到。按诊断纪律这属于
"再调窗口/降阈值"的牛角尖信号，故停手换路子：**归因需要（a）连续、且按颜色分侧的总分序列，
（b）金币的感知层产出**——前者是实时读数的活，后者是 §7#3，本就不属于这一层。

**离线数据给出的提示（`[待复核]`，不当结论）**：p1 里 4 个 `Δ总分 ≥ 90` 的时刻中，两次
（+141，分别伴随横幅 `极限变道`、`极限超车`）**超车计数并未增加**——即我方总分的增长与超车
计数**不同步**，方向上是"金币与极限动作主导、超车 30 分只是小头"的又一次旁证。

### 4. 阶段计时是**剩余时间倒计时**，且两阶段不对称 `[实测]`

`timer` 单段有效 73/76、**单调性零违例**（35→1）。跨会话：阶段 1 上限约 35 秒，阶段 2 约 4 分 50 秒
——与 §7#5 记录的「阶段 1 计时 00:28、阶段 2 计时 04:54」吻合。

### 5. 事件横幅是**持续显示的连击计数**，不是"事件一闪而过" `[实测]`

这是本轮**修正了的**一条。横幅文字 `极限超车×N` 会连续存在数百帧，且计数递增；它不是某次超车的
瞬时提示。实测序列（一轮之内，跨两阶段）：

- 阶段 1：先出现 `极限变道`，随后转为 `极限超车`，再累加到 `极限超车×2`；
- 阶段 2：`极限超车`（即 ×1）→ ×2 → ×3 → ×4 → ×5 → ×6。

推论：**连击档位是画面上可直接读出的字段**，不必靠分数增量反推——`RULES.md` §7#1（连击判定）
由此从"无素材"变为"有直读量"。注意横幅**只在阶段内首次「极限」事件之后才出现**（此前该位置
是护栏/远景），故判在场必须要求中文/数字，否则会把护栏认成横幅（见「复核判据」坑 1）。

### 6. 浮字是**贴着车跑**的，位置不固定 `[实测]`

`find` 在整条路面上搜到两类浮字：`+30`（反复出现，与 30/超车 系数同源）与 `+120`（以及更大的
`+180`/`+1880` 形态）。它们的归一化位置横跨 x 0.38–0.59、y 0.44–0.70——**没有固定位置**，
因为它浮在被超车辆/自车所在处。故：**浮字不能当固定 ROI 读**；`+120` 的语义（是否等价于
4×30、是否计入「我方总分」）仍待确认，**不能当"超车=120分"用**。

### 7. 画面自带「N米」是**对手车的距离标注**，不是可用观测量 `[维护者口径]`

这是本轮**纠正了的**一条错结论。原先记为"游戏自身给出到目标的距离，世界模型可直接受益"——
**错**。维护者口径：`N米` 标的是**对手车**的距离；对手是**幽灵车**，速度完全由双方得分决定
（分高则显示更靠前，反之更靠后），不参与物理场景、不会干涉本车。故：

- 它对驾驶决策**无用**——没有一个动作能改变它与本车的相对关系；
- 它是**分数差的另一个显示形态**，与右上双方总分冗余，不提供新信息。

**教训**：路面上的文字不都是"可用的世界观测量"，先问"这个量由什么决定、有没有动作能影响它"。

### 8. 阶段均速：我方约 124 分/秒、对手约 57 分/秒（两段各自独立）`[实测]`

出处是 `review_run timeline` 的阶段均速行（取"首个可信点 → 末个可信点"的整体均速，掉位数与
串位尖峰两类假读已剔）。**两段的我方速率几乎相同**（123.3 / 125.7），**对手也几乎相同**
（56.8 / 57.7）——对手是幽灵车、分数按固定曲线走（结论 7、`RULES.md` §4.9），两段接近是预期；
我方两段接近则说明这两轮开法相似。

⚠ **均值含事件突跳，不能当"巡航速率"使**：同一份 `timeline` 里相邻样本的 Δ/Δt 在无事件段
约 35/秒（与窗口里程 338/10 秒同量级），带事件段可到 190/秒以上。均值约为巡航段的 3.5 倍，
**提示事件的贡献占大头**——这正是决策层收益模型要抓的部分。它的来源分解（超车 / 连击 /
金币各折多少）**尚未闭合，但缺的已不是系数**：2026-09-18 起系数由官方规则页给全（里程
1 分/米、超车 30、社会车退场 180、动作 120、金币 30 分/枚），缺的是**归因**。同时窗口「合计」
与该窗口内比分增量对不上（实测比分增量大于合计），故合计不是"该窗口的得分"，两者仍是不可
换算的两个量（见缺口表）。

### 9. 归属必须**成对判**：两块面板半透明，背景会给两块染上同一偏色 `[实测]`

**这是本轮从数据里查出来的一条判据缺陷，也是一个教训。**

2026-09-17 第二轮实机数据里，`review_run check` 报出 **51 处"比分回落"**——那一场是
**`20260917_220453_p1`**（判据失效取决于**游戏内场景亮度**：该场墙钟是 22:04，画面却是白天
蓝天，"白天/夜里"说的从来不是时间）。今天重跑该场为 **0 处**——那 62 行归属异常已被
"归属异常行不进序列检验"滤掉（另两场各余 2 处 / 1 处，是掉位数假读，与本条无关）。
摊开原始行才看清：那 51 处不是分数在掉，而是**两块比分面板被判成了同一方**（62/69 行都写成
`本机(蓝)`）——物理上不可能，一块蓝一块红。两个块的值因此被混进同一条序列，来回取值就成了
"回落"。

**根因**：面板是**半透明**的，背景景物会给条带整体染色。白天蓝天背景下两块条带的饱和像素
**都偏蓝**（实测上块 B−R=+68、下块 +130），而判据原本是"单块绝对阈值：谁偏蓝谁是本机"——
于是两块都"偏蓝"，两块都成了本机。夜里深色背景场（20:04 那两场）没有这个公共偏色，所以
同一个判据在那里是对的——**这不是"阈值调小了"，是判据的形态不够**。

两条修法（都已落地）：

- **成对判**（`pair_sides`）：物理约束是一蓝一红，故用**两块之差**定归属，公共偏色被抵消
  （上块 68、下块 130 → 下块更蓝 → 下块是本机，与画面一致）；差值小于 40 则两块都弃权 `?`
  （多半是面板正在淡入淡出——实测正常场里也有单帧差 5.5 的样本）。**不猜**比猜错好。
- **采样收窄到最饱和的一撮**（饱和度最高 5%）：色条是实色块，饱和度显著高于背景与被染色的
  面板本身，故让色条而非背景主导（实测最小差值由 41 提到 86，分离更干净）。

**验证**：在问题现场的真帧上，成对判把 19 行"本机/本机"恢复成 17 行"对手上/本机下"（与画面
门牌一致）；在正常的三场上，成对判的结果与旧判据**完全一致**，只多了 1~2 处诚实的弃权
（两块太近的那些帧）。生产侧自 SCHEMA 3 起改用成对判并逐格记 `side_source` 留痕；离线探针的
`overlay` 也改成在图上标成对判的结果。

**顺带解掉的两个疑点**：

- **「得分速度」只为本方显示**：本机侧 100% 有读数（61/61、64/64、84/84），对手侧只有零星
  1~11 处——那是空区的假读（此前记的"对手速度 2/1/0"就是它）。故速度格与比分格一样，
  **必须按归属取、不能按位置取**。
- **"两块同判"这类故障值得当成数据质量事件报出来**：它不出现在任何行内标志里（每格都
  `trusted=True`、文本也都读对了），只有把整帧当整体看才认得出。故 `review_run check` 现在
  会显式报它，并把该行归属按 `?` 处理。

**教训（与结论 2、3 同源）**：单帧看着合理的读数，可能整段都是错的；**判据要利用对象之间的
约束**（一蓝一红、分数只增不减、合计 = 里程 + 30×超车），而不是只盯一个对象的绝对值。

## 复盘工具 `review_run.py`（读实时读数，不跑 OCR）

探针的 `timeline`/`formula` 是**离线重识别**（读帧、跑 OCR），它只能给稀疏样本；实时读数落地后，
"这一局的分从哪来"应该从**落盘的读数**复算——同一帧识别两次会给出两个答案，复盘不能再造一次判读。

`review_run.py` 因此只读录制会话里的产物（`hud.jsonl` / `frames.jsonl` / `pads.jsonl` / `meta.json`），
做的是**在读数之上做算术与不变量检验**：

| 模式 | 回答什么 |
|---|---|
| `check` | 这份读数**可用吗**：计数与 `hud_meta` 是否自洽、误差计数、与录制帧的对齐率、逐字段的可信/定值比例、假读清单 |
| `timeline` | 每个时刻各格的读数 + 每行的判定标签；比分按**归一后的敌我**列（面板上下互换不影响）；并给比分的增量归因（Δ/Δt 与画面「得分速度」并列）|
| `windows` | 左侧卡片的在场窗口切分：周期、时长、"窗内各格 爬升 → 定值"、跨窗定值是否同量级 |
| `sheet` | 出图（全帧缩略 + 左侧卡片放大 + 比分面板放大 + 判读标注），只挑**有争议的行**：违例 → 爬升 → 窗口边界 → 定值 |

**两条判据写在工具里，且只作用在"定值点"上**：

- **定值（settled）= 与上一次可信采样同值**（间隔 ≤ 1.5s）。爬升段的值"看着合理"
  （268/292/317/338 都是合法里程），但它只是滚动动画的中间帧——拿它算增量或验公式都会得到
  假结论（假违例、假来源）。故卡片三格的增量与公式检验**只用定值点**，非定值的可信行标 `ramp`。
  **这一位现在由生产侧给出**（`hud.py` 自 SCHEMA 2 起每格带 `settled`），工具优先读它、
  只在旧会话（SCHEMA 1）上按**同一规则**重算——两处口径逐字一致，不许各写一套。
- **比分单调不减**（掉一位数的假读实测存在且带 `trusted=True`：`18804`、`39`、`458`——行内标志
  拦不住，只能靠序列不变量）。回落样本列在 `check` 的「比分回落」并在 `timeline` 的归因里**跳过**；
  串位尖峰（值骤高又掉回）同样剔除，判据见 `side_series`。

**它复现出的结果**（2026-09-17 那两场，各 67 行）：计数自洽、误差计数全 0；与录制帧精确同帧
26/67；公式在定值点上**零违例**；每段 4 个窗口、周期中位 9.9 秒、时长中位 3.0 秒、跨窗里程定值
338–344；阶段均速我方约 124 分/秒、对手约 57 分/秒（结论 8）。这些数字都可由命令重跑得到，
别处不必再抄一份。

**它会主动报出的数据质量事件**：① **归属异常**——两块比分面板被判成同一方（物理上不可能，
见结论 9），该行归属按 `?` 处理、不进序列检验；② **比分回落**——掉位数 / 串位尖峰两类假读；
③ 行内 `flags`（`合计 < 里程`、单字面板读数）。**旧格式（SCHEMA ≤ 2）的会话在白天蓝天场会
成片触发第 ① 条**，那是生产侧单块判据的历史缺陷，不是这批数据本身的问题。

| `rate_top`/`rate_bottom` 的定义 | **半数已解**："只为我方显示"已确认（结论 9）；量级仍对不上 | 与 `d(总分)/dt` 未吻合；本轮观测：读数集中在 `11+30k` 档位上（41/71/101/131/161/191/221/251/281/581/641，30 与本作的超车当量同值），另有少数离群值（2/6/7/20/27/32/39/40/126/132/159/163/164——其中一部分正是**对手那一块空区的假读**）。稳态巡航时它显示 41，而同期 `Δ比分/Δt` ≈ 35~37/秒——同量级不等，且**明显滞后于分数跳变**（分数突跳后它要几个采样才跟上），故像是**平滑显示**而非逐样本速率。判定它需要一个"分数匀速增长"的长区间；`review_run timeline` 已把两者并列，先不下结论 |
| `+120` 的语义 | **两来源同值，靠画面分** | 官方系数下**动作 120 分/次**、**金币 30 分/枚**（半空一组 4 枚 = 120）——两种来源同为 120，**单看数值分不出**，要靠画面内容（有无金币 / 跳台）判别。是否计入我方总分：浮字即得分弹字，推定计入，待比分序列实证 |

**另有一项架构决策**（不属本实验）：实时读数（模块内观察线程写 `hud.jsonl`）需要插件内的
OCR 引擎，而 `speedrush` **不能** import `treasure.ocr`（插件自包含契约：整个目录拷走即卸载）。
故把引擎段抽到 core（共用者今天已真实存在两个）——**已于 2026-09-17 落地为
`maaracing_master/plugins/speedrush/hud.py`**：低频采样线程 + 同会话 `hud.jsonl`，与
`frames.jsonl` 按 `frame_id` / `ts_ns` 对齐。本探针按实验自包含约定**不** import 它，
故探针内保留一份最小引擎——那份副本只服务离线复核，不构成生产口径的第二真源，
但**它的调参需要跟着 core 走**（改 core 时同步核对）。区域**数据**则是单一真源：本探针
`--rects` 缺省读插件内那份，两份 rect 已合并（见上文「ROI 真源」）。
