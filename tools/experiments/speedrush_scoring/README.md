# speedrush 记分观测与规则实测（C 类实验，2026-09-17）

回答的问题：**「极速狂飙」驾驶阶段的分数是怎么来的**——各加分项折算多少分、分数在画面上
以什么形态出现、能否从录制数据里事后复算。这是「胡萝卜模型」（决策层收益模型）的输入规格：
规则没测清之前设计收益模型，等于拿印象当系数。

**先读**：游戏规则事实 [`RULES.md`](../../../maaracing_master/plugins/speedrush/RULES.md)（§4.2 加分项、§4.8 计分、§7 待实测）；
驾驶控制路线 `docs/plan/speedrush-control-route.md`（本机文档）。

***

## 方法与判据

- **素材**：`data/speedrush/demos/` 下 4 个已录会话（2 轮 × 2 阶段，2408 帧，1280×720）。
  录制帧含完整 HUD，故**规则实测不必等新实机**——离线即可读数。
- **读数链路**：`probe_hud_ocr.py`。标定用 `discover`/`scan`（带文本检测，先定位再定 ROI），
  生产口径用 `read`/`timeline`/`formula`（关文本检测，与 treasure OCR 同口径：固定 HUD
  文字框下 det 是冗余计算）。
- **ROI 来源**：`hud_regions.json` 的每一格都由 `scan` 的**按位置统计**定出（不是目测）。
  ⚠ 早期的按**文本**聚合会漏掉数值字段——它们每帧都不同，会全部塌成 count=1
  （`我方总分` 就这样被漏过一次）。
- **面板在场闸门**：`field_on_dark()`。左侧信息面板会闪烁、且有"矮版"变体（不显示合计），
  直接对 ROI 做 OCR 会读到天空、产出垃圾值。判据是 ROI 内暗像素占比（纯 numpy，零 OCR 开销）。
- **标尺独立性**：读数来自画面（PIL/cv2 读盘 → RapidOCR），与"策略应当怎样"无关；
  结论一律以**同一局内多个字段互相印证**为准（见下），不靠单点。

## 结论

### 1. 合计分值 = 里程 + 30 × 超车 `[实测]`

同帧三个字段同时可读时，逐点比对（`formula` 模式，4 会话 60 个有效采样点）：

| 超车 | 合计 − 里程 | 采样点数 |
|---|---|---|
| 0 | **0** | 多点 |
| 1 | **30** | 8（跨 p1 两段） |
| 3 | **90** | 4（p2） |
| 4 | **120** | 4（p1） |
| 5 | **150** | 2（p2） |

五个档位、两个阶段独立吻合；并与 `RULES.md` §7#4 已记录的观测
「里程 338 + 超车 1 → 合计 368」（差 30）一致。**故 §7#4 的「里程/超车折算」部分就此定案**，
不必再做一次实机实验。

### 2. 里程是累计里程（1 分/单位），不是"里程分" `[实测]`

同段会话内里程单调递增（约 9 单位/秒，与车速同量级），且合计 = 里程 + 30×超车 中的系数为 1。

### 3. 里程 + 超车 只占总分的一小部分 → **金币才是主要得分来源** `[实测，单会话]`

同帧比较左侧「合计」与右上大字「我方总分」：

| 时刻 | 合计（里程+超车） | 我方总分 | 占比 |
|---|---|---|---|
| 阶段中段 | 402 | 2065 | 19.5% |
| 阶段后段 | 523 | 3495 | 15.0% |
| 阶段末帧 | 523 | 4206 | **12.4%** |

其余约 88% 来自金币、连击等非里程非超车项——与 `RULES.md` §4.2 的
「主要加分项＝金币」`[权威]` 独立吻合。**这条直接决定胡萝卜模型的权重取向：吃金币的
优先级高于贴车超车。**（跨会话复核见"缺口"。）

### 4. 阶段计时是**剩余时间倒计时**，且两阶段不对称 `[实测]`

`timer` 单段 73/76 有效、**单调性零违例**（35→1，历时 38.6 s）。跨会话：阶段 1 上限约
35 秒，阶段 2 约 4 分 50 秒——与 §7#5 记录的「阶段 1 计时 00:28、阶段 2 计时 04:54」
完全吻合。**故 §7#5 定案：是剩余时间，且两阶段时长不对称。**

### 5. HUD 元素清单与可读性 `[实测]`

| 元素 | 位置（归一化） | 有效性 | 备注 |
|---|---|---|---|
| 阶段:N | (0.072,0.039,0.155,0.096) | 32/32 | 大字，稳定 |
| 计时 | (0.073,0.098,0.156,0.146) | 73/76 | 倒计时 |
| 里程 / 超车 / 合计 | 左侧面板内三格 | 面板在场时 | 面板会闪烁、有矮版变体 |
| 我方总分（大字） | (0.79,0.07,0.90,0.13) | **76/76** | 当前最可靠的主通道 |
| 得分速度 | 两侧各一组标签+值 | 不稳 | 值与 `d(总分)/dt` 未对上，待查 |
| 血量（两侧） | (0.93,0.12) / (0.94,0.24) | ~60% | `[权威]` 血量由积分差决定 |
| 事件横幅 | (0.076,0.488,0.151,0.524) | 22/32 | **含连击数**：`极限超车×2`、`极限变道` |
| 中央浮字 | (0.46,0.61,0.52,0.68) | 偶发 | **`+120`**，与极限超车同现 |

### 6. 两条旁证（`RULES.md` 需人工复核后回填）

- **贴车/超车有 `+120` 浮字**：与维护者口径「贴近街车一辆 120 分」一致。但**注意口径区分**：
  左侧「合计」里每辆超车只算 **30 分**，而 `+120` 是另计的事件浮字——两者不是同一个量，
  且 `+120` 尚未确认是否计入「我方总分」。**这条不能直接当"超车=120分"用。**
- **画面自带「N米」距离标注**（`79米`/`21米` 等，位于路面车辆上方）：游戏自身给出到目标的
  距离，世界模型可直接受益，不必自行由 y 反推距离。

## 缺口与下一步

| 项 | 状态 | 需要什么 |
|---|---|---|
| §7#4 金币/连击折算 | 未解 | 金币数不是 HUD 字段；只能从「我方总分 − 合计」的增量与画面金币对齐反推，需要**金币可见的连续帧段**——已有素材够，但需与检测/人工标点配合 |
| §7#1 连击判定（累积/清零） | 未解 | 事件横幅给连击档（×2/×3），配合分数增量可查时间窗与中断条件 |
| §7#2 极限超车触发 | 未解 | 已有 `极限超车` 与 `+120` 帧；需与「贴身距离」观测量对齐（距离标注 `N米` 可用） |
| §7#3 金币的车道分布规律 | 未解 | 需金币的横向位置序列（属感知层产出） |
| 结论 3 的跨会话复核 | 单会话 | 再跑 p2 一段即可 |
| 得分速度读数 | 未对上 | 值与 `d(总分)/dt` 未吻合，可能它是平滑量或另有定义；先不下结论 |

**另有一项架构决策待定**（不属本实验）：实时读数（模块内观察线程写 `hud.jsonl`）需要
插件内的 OCR 引擎，而 `speedrush` **不能** import `treasure.ocr`（插件自包含契约：整个
目录拷走即卸载）。故要么把引擎段抽到 core（共用者今天已真实存在两个），要么在插件内复制
一份——后者会让 ORT 线程/亲和性那套硬测出来的调参出现第二份真源。
