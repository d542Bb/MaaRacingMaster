## 〇、先钉死两条结构性事实（后面所有家族都建在这上面）

### 事实 A：均匀 patch 的 ViT 里，「token 数」与「空间采样密度」是**同一根轴**

DA-V2 的 patch 恒为 14（DINOv2 ViT-S 定义）。输入短边 S ⇒ patch 网格 `(S/14) × (W/14)`，换算回原始 1280×720 帧：

| 档 | 短边 S | patch 网格 | 单 token 覆盖（原始帧像素，横/纵） | token 数 |
|---|---|---|---|---|
| @336 | 336 | 24×42 | ≈ 30.5 × 30.5 | 1008 |
| @448 | 448 | 32×56 | ≈ 22.9 | 1792 |
| @518 | 518 | 37×65 | ≈ 19.7 | 2405 |

**结论**：在不改模型的前提下，想让深度场的空间采样变细，**只能加 token**；想让 token 变少，**只能把采样变粗**。二者不可解耦。这一条是后面「哪些收益必须买更多 token」的判据来源。

要打破这条轴，只有三条出路，也正好是后面家族的三分：
- **(a) 重新分配 token**——总数不变，把预算从「不需要精度的地方」挪到「需要精度的地方」（家族 2、4、5）；
- **(b) 换一个信号提供精细定位**——深度模型的网格不变，边界精度由另一模态（RGB 边）补（家族 6）；
- **(c) 削每 token 的成本**——网格不变，让同样预算装下更多 token（家族 7、8）。

### 事实 B：DPT 头的空间格点**不是**瓶颈——它在两个档上都已经比 token 网格细 4 倍

读官方源码 `depth_anything_v2/dpt.py`（【官方源码】）：

- 取主干中间层 token：`vits: [2,5,8,11]`；
- 四路 Reassemble 的上采样阶梯是 `ConvTranspose2d(k=4,s=4)`（×4）、`ConvTranspose2d(k=2,s=2)`（×2）、`Identity`（×1）、`Conv2d(k=3,s=2)`（÷2）——**最细一路到 4×patch 网格**；
- refinenet 融合后 `output_conv1` 在 4×patch 网格上出图，再 `F.interpolate(..., (patch_h*14, patch_w*14))` **双线性放大 3.5×** 回到输入分辨率，最后 `output_conv2`（3×3 + 1×1 卷积）在**全输入分辨率**上出 1 通道。

换算成原始帧：头的最细格点 = 输入/3.5 ⇒ @336 约 **7.5px**、@518 约 **4.9px**——**两档都远细于单 token 覆盖（30.5 / 19.7px）**。

**结论**：头不产生新信息，只把主干 token 网格的信息插值放大（与本目录既有结论一致，此处给出源码级依据）。**336→518 的精度提升不在头上**——头在 @336 就已经有 7.5px 的格点。丢信息的是**编码器的 token 特征本身**。这一条直接排除「解码器侧省而编码器不省」作为精度路线（见家族 9）。

## 一、地基问题：336→518 的钱花在哪、又买到了什么

### 1.1 花钱侧：token 数是唯一自变量的超线性曲线

折叠会话下的实测（同批可比，行内）：

| 档 | token | p50 (q4f16) | token 比 | 时延比 | 纯注意力比（∝N²） |
|---|---|---|---|---|---|
| @336 | 1008 | 22.5ms | 1.00 | 1.00 | 1.00 |
| @448 | 1792 | 46.9ms | 1.78 | 2.08 | 3.16 |
| @518 | 2405 | 90.8ms | 2.39 | 4.04 | 5.69 |

时延夹在「线性 ∝N」与「二次 ∝N²」之间（4.04 落在 2.39 与 5.69 之间）——即**注意力二次项与线性项（patch embed / MLP / 头）混合**，且 DML 上还叠了一层超线性（既有记录：1008→1944→3488 token 时延 22.5→80.3→311ms，比值 ×1.9→×3.6、×1.8→×3.9）。所以**任何以「省 token」为手段的方案，其收益按超线性折算**，不能按 token 比例线性外推。

### 1.2 买到侧：把「精度」拆成四层，只有两层与分辨率有关

| 层 | 是什么 | @336 | @518 | 是不是瓶颈 |
|---|---|---|---|---|
| **L1 编码器 token 网格** | 主干对深度场的空间采样率 | 30.5px/token | 19.7px/token | **是**（提升主要来自这里） |
| **L2 解码器格点** | DPT 头重建的空间格点 | 7.5px | 4.9px | **不是**（两档都已细于 L1，见事实 B） |
| **L3 全局注意力的样本量** | 相对视差的归一化锚与长程推理的内容量 | 1008 | 2405 | **是**（裁切实验已证锚不可省） |
| **L4 位宽/量化地板** | q4f16 的表示误差 | 被 L1 误差淹没 | 触及地板 | 当前**不是**，但抬高分辨率后会变成是 |

**L4 的内部依据**：q4f16 带固定量化地板（仿射校正残差约 0.014）；预算相关档位被分辨率误差淹没、**392 档起可见、518 锚点档即地板**。同时 int8/uint8 档存在「伪台阶」风险（相邻同值 24.15%、邻居跳变 p95 ≈ 近路量程的 4%，与目标台阶同阶），而 q4/q4f16（权重-only）输出保持连续、无色带，只有平滑低频漂移。

**推论**：**任何把分辨率往上推的路线，都必须同时复核位宽**——因为在 @336 被淹没的量化误差，在更高分辨率下会重新成为绑定项。这是「省下的钱换更高分辨率」这条启发式的隐含代价项。

### 1.3 「必须有更多 token」vs「同样 token 更准的位置」——分界线

**必须买更多 token 的收益（不能靠重新分配拿到）**：
- **L3 全局锚的样本量**：相对视差按整帧内容自归一，天空/远景是尺度锚。裁切实验已证：**内容一旦被删，对比度被压平、深度带压窄紊乱**——这不是「token 少了」而是「内容分布变了」。所以锚的**内容**不可省。
- **小结构的分辨**：窄台阶要分成两个 token 才可能在特征上分离。低于 token 尺度的结构，主干在特征层就没有对应自由度——后置上采样无法凭空造出。

**「同样 token、更准的位置」能拿到的收益（前提是内容不被删）**：
- **边界局部的采样密度**：把天空/远带的 token 预算挪到路带（家族 2、4、5）。这类方案只要做到**「保内容、只改采样密度」**，就与裁切有本质区别——裁切是把内容删掉，重分配是把内容压小。
- **边界的亚 token 定位**：由另一模态（RGB 边）把边界钉到亚 token 精度（家族 6）。此时深度模型的网格不变，精度来自外部信号。

**这条分界线是本报告最重要的判据**：凡是「删内容」的省算力方案，都会被锚问题否决（已由裁切实证）；凡是「压缩内容/后置补细节」的，锚可以保住，值得作为候选。

### 1.4 一个必须摆在最前面的现实检查：本任务的读数是一根**线**，不是一张图

消费侧要的是「每侧边界在车道坐标里的位置」——生产实现是**在源行上做直线拟合**（`depth_geo._fit`，两轮剔点后取中位评估）。一条 3D 直线在画面上的投影是直线 ⇒ 每侧只有 2 个自由度。

**含义**：逐行噪声在拟合里被平均掉，**约束最终读数精度的不是逐行分辨率，而是系统性偏置**。而当前已知的系统性偏置恰恰是：
1. **自车邻近晕影**（±3~6% 视差，横向溢出 150~250px）——幅度与目标台阶同阶甚至更大；
2. **R 侧弱台阶**（墙侧本底仅 +4.4%，贴门）。

这正是实机复核的结论形态：**「几何没错，错的是读哪一行和每拍成本」**，以及源行规则下 **@518 无优势**（覆盖 ≤17/44、双侧≈0），而 L 侧 @518 更干净（dev p90 0.09 vs @336 的 0.15）。

**因此，本报告对绝大多数「提升精度」的机制家族打上同一条标记**：
> ⚠ **待晕影治理后再评估** —— 若某机制声称的精度提升量级小于晕影污染（±3~6% 视差），在晕影治理前无法与污染区分；其探针必须在**晕影掩码外的子区域**上评估，或先把门/挖除带做到晕影可忽略。

## 二、机制家族

每个家族统一给五项：**锚怎么保住 / 代价模型 / 代表工作（训练无关→需微调→需重训分层）/ 部署链兼容性 / 44 帧金标最小探针形态**。

金标基建（本目录已有，探针直接复用）：`gold_labels.csv`（44 帧，每侧两点直线 + 类别）、`gold_score.py`（逐行 dev）、`probe_readband.py`（源行/评估行拆分）、`probe_halo_strip.py`（晕影条带图）、`depth_review/npy/*__d336q4f16.npy`（离线缓存）。

### 家族 1：内容自适应 token 合并（ToMe / G2TM 类）

**机制**：把相似的 token 合并成一个代表 token，**合并后仍参与完整全局自注意力**（被合并 token 代表多个 patch，但 attention 仍在全部内容上跑）。

**锚怎么保住**：✅ 内容不删——这是合并与剪枝的分水岭。ToMe 原文：「unlike pruning, ToMe is able to merge a large number of tokens both in the background and the foreground without losing information」。注意力仍在全内容上做，锚的统计量不丢。

**代价模型**：每层合并 r 个 token，L 层累计 r·L。ViT-S/16（AugReg）分类域：r=16 → 81.41%→77.01%（**−4.40**），吞吐 1.93×；原文总述「ViT-B/S/Ti 在 2× 速度下精度掉 4~5%」。

**代表工作**：
- **ToMe**（arXiv:2210.09461，Meta）——训练无关。**官方补丁只覆盖 timm / MAE / SWAG / DeiT，无 DINOv2/DPT**；论文**没做稠密预测实验**（分割只在结论里列为 future work）。
- **G2TM**（arXiv:2609.18279，2026-09）——"Decoder-Agnostic Token Merging"。图连通分量（4 邻域余弦相似度阈值 τ 割边 + BFS）合并、**只在浅层插一次**、按需 unmerge。ADE20K 分割 ≤2 mIoU 换 22~47% GFLOPs、最高 74% 吞吐。**明确结论：合并效果是编码器属性、与解码器无关**；**稠密预测比分类敏感得多**；分割需微调（off-the-shelf 只在 ViT-L 上成立）。
- **DiffRate / EViT / Token Pooling** 等：可微/注意力打分路线，需训练，且属剪枝类（删而非合），锚风险更高。

**⚠ 对我们的决定性负面证据（G2TM §Limitations）**：
> **DINOv2 预训练下 token 合并崩溃**——第 1 层 −5.6 点、第 2 层 −8.8 点，是该研究全表最大降幅。**原因：DINOv2 相邻 token 的余弦相似度几乎全部挤在 0.99~1.0，相似度判据丧失判别力，合并变成 "uninformed"。**

**我们的编码器正是 DINOv2 ViT-S/14** ⇒ 基于「相似度」的内容自适应合并，在 DA-V2-S 上**先天地基不稳**。这不是工程问题，是判据失效。

**另一条边界**：G2TM 明确「吞吐收益只在 baseline 吞吐低于约 100 FPS 时成立；高于此点合并自身开销抵不过注意力节省，**吞吐反而下降**，典型是 ViT-T/ViT-S 等轻量模型」。我们折叠后 @336 约 44 FPS、@518 约 11 FPS——**@336 落在该边界附近**，属需实测区。

**部署链兼容性**：❌ **硬冲突（见 §三）**。合并需要 `Gather`/`Scatter` 索引张量，而 **DML EP 对 Int64 索引算子崩溃**；且内容自适应 ⇒ 每帧 token 数不同 ⇒ 动态 shape ⇒ **折叠失效（6× 代价）**。ToMe 官方 repo issue #32：timm+ToMe 的 ONNX 导出失败，无解；**不存在 DA-V2+ToMe 的 ONNX 化先例**。

**44 帧金标最小探针**：离线**不导出 ONNX**，直接 PyTorch 跑 DA-V2-S + ToMe(r 网格)，@518 输入、看 `gold_score` 的 L/R dev p50/p90 与覆盖率随 r 的变化。**判据**：若 r 增大时 L dev p90 立刻劣化到 @336 水平，即坐实「DINOv2 相似度判据失效」在本域同样成立，本家族整条关闭。成本：一个下午，零部署改动。

### 家族 2：固定空间模式的 token 重分配（content-blind 合并）

**机制**：**不用相似度**，用**固定的空间先验**决定哪些 token 合并——例如「画面顶部（天空/远带）的 token 按固定分组平均，路带保持原样」。合并表是**编译期常量**，与帧内容无关。

**为什么这是本报告里最值得注意的构造**：它同时绕开两个死结——
1. **绕开 DINOv2 判据失效**：不问模型「哪些 token 相似」，只按位置分组 ⇒ G2TM 那条负面结论对它不适用；
2. **绕开动态 shape**：合并表固定 ⇒ 每层 token 数是**编译期常量** ⇒ ONNX 静态形状与折叠**理论上可保**。

**锚怎么保住**：✅ 合并而非删除，被合并的远处 token 仍作为代表进入全局注意力。**内容不删**——与裁切有本质区别。

**代价模型**：@448 网格 32×56=1792 token，若把顶部 30% 行（≈538 token）按 10:1 压成 ~54 个 ⇒ 省 ~484 token ⇒ 约 1308 token。按内部超线性曲线折算，落在 @336 与 @448 之间。**收益 = 用「天空的采样率」换「路带的采样率」**：路带保持 @448 密度（22.9px/token），总 token 数却接近 @336 档。这就是事实 A 里「重新分配」的正解形态。

**代表工作**：**查不到**把「固定空间合并表」直接用于单目深度的工作。最接近的是：
- ToMe 的 **decreasing schedule**（每层合并数按固定线性表递减）——但合并**对象**仍是内容自适应的；
- **SparseViT**（arXiv:2303.17605）的窗口级激活剪枝——用 **L2 范数**打分（比相似度简单、更鲁棒），复制未选窗口特征；但它是**删/复制**不是合并，且只针对窗口式 ViT（Swin），需 adaptation+搜索+微调；
- **DepthCache**（arXiv:2603.10469，2026-03）——用深度分区决定合并比（近场保、远景压），**训练无关、在编码器之外**；但**它直接吃现成深度图**（仿真器/RGB-D），不估深度——对我们的场景是循环依赖，只能借其「按区域差异化合并比」的思想。
- ⚠ 这条路线本质上是**自研图手术**，属 A 类投入，无现成实现可抄。

**部署链兼容性**：⚠ **理论可行、工程未验证**。固定合并表 ⇒ 静态形状 ✅；但 `Gather`/`Scatter` 索引算子仍在 DML 的 Int64 雷区（§三），且 DML 折叠成单节点的前提是「整图可融合」，插入 gather/scatter 大概率**打破单节点融合**、把 421 节点级的派发开销请回来。**未验证项，必须先做算子级探针**。

**44 帧金标最小探针**：两步。
① **离线 PyTorch 正确性探针**：@448 + 固定顶部合并表，对 44 帧金标出图，比 dev/覆盖率 vs 全帧@336 与全帧@448 两个参照。**判据**：若 dev 优于 @336 且接近 @448 ⇒ 重分配假设成立，值得投工程；若不优于 @336 ⇒ 路带的精度本来就不是被 token 密度绑住的（回到晕影），本家族降级。
② **仅当①通过**才做 ONNX 探针：固定表导出后测折叠会话节点数与 p50（对 2.6ms 地板与 22.5ms 基线）。

### 家族 3：跨帧 token 门控与复用

**机制**：帧间高度重叠 ⇒ 只重算「变化了」的 token，未变化的复用缓存特征。

**锚怎么保住**：✅ 单帧内注意力仍覆盖全部 N 个 token（只做增量更新），全局锚不丢。

**代表工作**：
- **Eventful Transformers**（CVPR 2024，arXiv:2308.13494）——token gating：按误差 L2 范数取 top-r 更新，未选 token 走 buffer 复用；`qkᵀ` 与 `Av` 走 delta 更新。视频检测 1024 分辨率 r=768：GFLOPs 467.4→122.3（**3.8×**），mAP50 仅 −1.68%；动作识别 2.4×/−1.62%。**一般免重训**。
  - **两个硬伤**：① wall-clock 只 1.74×（vanilla PyTorch、未优化，需自定义融合核才能兑现 FLOPs）；② **attention 矩阵缓存开销巨大**（1024 分辨率全局注意力层的 `A` 需 805MB fp32 / 403MB fp16）。
  - 未测分割/深度；窗口注意力块只能加速 token-wise 操作。
- **DepthCache**（arXiv:2603.10469）——跨帧**渐进**合并（把一次合并摊到 W 帧），深度分区差异化合并比 + 语义/几何双保护；1.07~1.28× 加速、<1% 成功率损失。**但它需要外部深度输入，且受 Amdahl 定律限制**。
- **Video Depth Anything / DA3-Streaming** ——属**换模型**（时序头/分块 keyframe），不是既有模型的可插拔项。

**代价模型**：理论 2~4× FLOPs；但**对我们是「每拍成本」而非「总吞吐」**——而延迟已异步化，latest-only 槽已把 90ms 与控制环解耦。**本家族省下的钱若只用于提更新率，对本任务零收益**（启发式：延迟不是痛点）。唯一正当用法是**把省下的 token 预算换成更高分辨率**。

**部署链兼容性**：❌ **硬冲突**。门控掩码逐帧变化 ⇒ 动态 token 数 ⇒ 静态形状击穿；且同样落在 Int64 索引雷区。**除非**把掩码固定（那就退化成家族 2，且失去自适应）。

**44 帧金标最小探针**：本目录已有连续帧缓存与晕影条带工具，可离线跑「相邻帧 token 差量」统计，回答**先验问题**：本域相邻帧（~20Hz）的 token 变化比例是多少？若变化比例本就 >50%，跨帧复用上限很低，家族 3 直接关闭——**这个统计不依赖任何模型改动，最便宜，建议先做**。

### 家族 4：非均匀/视觉中心重采样（foveated warp，输入空间）

**机制**：**不动模型**，只动预处理——对输入做固定的非均匀重采样：把天空/远带**压扁**、把路带**拉伸**，总像素数不变、token 数不变，但路带的采样密度升高。

**锚怎么保住**：✅ **内容不删**——天空仍然在画面里（只是占的像素少），与裁切的本质区别在此。但**风险真实**：裁切实验的教训是「内容分布偏移 ⇒ 对比度被压平」；压缩天空是**部分**的分布偏移，程度介于全帧与裁切之间。**这是本家族唯一需要实验裁决的点。**

**代价模型**：**零模型代价**——重采样在 preprocess 里做（固定仿射/分段线性映射），token 数、时延、折叠全部不变。代价只有一处：读数带的坐标需按同一映射做仿射迁移（机械换算），以及**质量风险**。

**既有内部旁证**：本目录已测过一档「带→变形 336×588」（横向压缩 2.1×）：**同 token 数（1008）、36.9ms**（比全帧@336 的 22.5ms 慢，疑输入内存布局/热漂移，复测前不作数），**质量待金标**。说明这条路的**成本端基本免费**，瓶颈全在质量。

**代表工作**：
- **FlexiViT**（arXiv:2212.08013）给出理论依据：patch size 与位置编码可在推理时 resize，**同一套权重可在多种采样密度下评估**，且检测任务上「最优 patch size 不一定是最小的、按 patch size 调优优于直接用最小」——支持「采样密度是可以按区域/按预算调的资源」这一视角。
- **Foveated Diffusion / Foveated Dynamic Transformer（FDT）**（arXiv:2607.09480，2026-07）——非均匀 tokenization，把高分辨率 token 集中在 ROI。属「非均匀采样有效」的一手佐证，但都在生成/MLLM 域。
- **查不到**把 foveated warp 用于**单目相对深度 + 游戏/驾驶域 + 推理引擎**的工作。

**部署链兼容性**：✅✅ **全家族里最好的一档**。纯 preprocess 改动，ONNX 图与折叠零影响，DML 完全无关。唯一要动的是坐标映射的标定与回归锁。

**44 帧金标最小探针**：**这是投入产出比最高的探针**。固定一条垂直分段线性映射（如「y<340 压缩 2×，y∈[340,715] 拉伸 1.3×」），把 44 帧按该映射重采样后喂现有折叠会话（形状不变、代码不动），比 `gold_score` 的 L/R dev、覆盖率、双侧同现。**判据**：路带纵向采样密度升 30% 而 dev 不劣化 ⇒ 找到了一条免费的分辨率来源；若 dev 显著劣化 ⇒ 分布偏移成立，与裁切同判。

### 家族 5：亚 token 超分与 token 扩展

**机制**：用一个小模块把「重要的 token」**放大成多个 token**（或直接提高其有效分辨率），把算力集中到 ROI。

**锚怎么保住**：✅ 原 token 序列保留，扩展是**加法**不是替换；全局注意力仍在全部内容上。

**代表工作**：
- **Blink**（CVPR 2026，arXiv:2512.10548）——**TokenSR**：3 层 2D 卷积 + ReLU 的轻量模块，把显著 patch 的 token 超分成多个 token 插回序列；**骨干全程冻结，只训 TokenSR**（KL 散度对齐「裁剪图 token」作参考）。消融里 DTR 模块贡献最大（−41.07）。
  - ⚠ 注意其方向：**它增加 token 数**（在显著区），因此是**重分配**（从非显著区省 token 换显著区加 token），不是净省算力。
- **Guided/Depth SR**：见家族 6（那是后置放大，机制不同）。
- **FlexiViT 的 patch resize**：同一模型换 patch size ⇒ 等价于换采样密度，属家族 4 的模型侧对偶。

**代价模型**：净收益取决于「省下的非显著 token」能否覆盖「扩出的显著 token」。对本任务：非显著区=天空/远带，可省空间大；显著区=路带。理论上可行，但**需要训练 TokenSR**（我们当前无训练基建——不过 TokenSR 只有 3 层卷积，是最小的训练项）。

**部署链兼容性**：❌ **扩展/插入 token 是动态 shape**（扩展数取决于显著性）⇒ 折叠击穿；固定扩展表则可退化为静态，但那样又变成家族 2。索引算子同样触 DML 雷区。

**44 帧金标最小探针**：先答**更便宜的前置问题**——路带内「边界 token」与「非边界 token」的可分性。若在 @336 的 token 特征上，边界 token 与邻近路面 token 本来就不可分（特征余弦相似度同高），则超分也分不出来。**这个统计只需一次前向 + 特征导出，不需要训练**。

### 家族 6：跨模态引导细化（深度网格不变，RGB 补边界精度）

**机制**：**编码器完全不动**（仍跑 @336 折叠档），在输出侧加一个**高分辨率、轻量**的细化模块：输入 = 低分辨率深度图 + **全分辨率 RGB**，输出 = 边界被钉到 RGB 边上的高分辨率深度。

**锚怎么保住**：✅✅ 深度模型的输入、上下文、锚**一字未改**——锚问题在本家族根本不存在。这是它与家族 1~5 的结构性差异：**它不试图让模型看得更细，而是让另一模态提供细定位**。

**代价模型**：细化模块在全分辨率上跑，但只是几层卷积 ⇒ **成本对像素线性**（对比主干的二次注意力）。ONNX/DML 上卷积是原生算子、静态形状、可融合。**这是全家族里唯一「成本可控且不碰锚」的组合。**

**代表工作（分层清楚）**：
- **训练无关（滤波类 F）**：Joint Bilateral Filter、Mutually Guided Image Filtering、Unsharp Mask Guided Filtering、Weighted Guided Image Filtering with Steering Kernel（GDSR 综述 ACM CSUR 2023 的 **F 类**）。经典、免训练、可解释，但精度低于学习类。
- **需训练（学习类 L）**：
  - **NAIMA**（arXiv:2604.04407，2026-04）——**语义感知 GDSR**。用**冻结的 DINOv2 ViT-S/14** 提语义 token，经交叉注意力（GTA 模块）选择性注入到深度编码里，抑制「误导性 RGB 边」。NYU_v2 训练 200 epoch；16× 下 RMSE 比次优低 3.14%~6.78%。输入 = **稠密低分辨率深度 + 高分辨率 RGB**（与我们的形态完全一致）。
  - **Hierarchical Edge Refinement Network**（IEEE 2024）、DAGF、SGNet、DORNet 等（L / L&F 类）。
- **失效模式（必须记住的名字）**：**texture copying / cross-modal misalignment**——RGB 里的颜色纹理（车道虚线、横向标线、夕阳反光团）**并不对应真实深度不连续**，朴素融合会把 RGB 的表面纹理当深度边复制过去，产生伪影与模糊边界。NAIMA 的解法是用语义先验判断「哪些 RGB 边是真实几何边」。

**⚠ 对本任务的双面性**：本目录已实测「三类污染物（白虚线/横向标线/夕阳反光团）全部归入路面」——**RGB 侧它们恰恰是有强边的**。所以：
- **坏消息**：朴素 guided filter / bilateral 会**把路面标线的边复制成假深度边**，直接把污染物变成伪台阶；
- **好消息**：NAIMA 的语义门控正是针对这一类失败设计的，且它用的语义编码器（DINOv2 ViT-S/14）**与我们主干同源**，架构上自洽。
- **成本/风险对照**：训练无关的滤波类**先试**（零训练），若 texture copying 不可接受，再考虑轻量学习类。

**部署链兼容性**：✅✅ 卷积 + 逐元素运算，DML 原生、静态形状、无索引算子。**与折叠会话串联时需注意**：会多一个图/节点，但代价线性且可测。

**44 帧金标最小探针**：**与家族 4 并列性价比最高**，且可完全训练无关地先做。
① 用现成 @336 折叠输出 + 全分辨率 RGB，跑**经典 guided filter**（`cv2.ximgproc.guidedFilter`，若 OpenCV-contrib 可得）或联合双边上采样，出高分辨率深度；
② 在 44 帧金标上比 dev/覆盖率 vs 未细化的 @336 基线；
③ **同时统计 texture copying 的代价**：污染带（白虚线/横向标线/反光团）区域内的伪台阶数（用 `probe_step_detect` 的既有判据）。
**判据**：dev 改善 > 污染物引入的伪台阶代价 ⇒ 值得；否则上 NAIMA 式的语义门控。

### 家族 7：主干家族替换（线性注意力 / 窗口 / SSM / CNN）

**机制**：换一个「成本对像素不那么超线性」的主干，从而在高分辨率下便宜。

**锚怎么保住**：取决于新主干。线性注意力/窗口注意力**仍是全局或准全局感受野**，锚可保；CNN 靠堆叠获得有效大感受野，锚的载体不同（无显式全局归一化）。

**代表工作**：
- **EfficientViT**（ICCV 2023，MIT HAN）——**多尺度线性注意力**（ReLU 线性注意力 + 卷积补局部 + 多尺度聚合），专门为高分辨率稠密预测设计。Cityscapes 上无精度损失下比 SegFormer 快 **8.8×**、比 SegNeXt 快 3.8×；超分比 Restormer 快 6.4× 且 PSNR +0.11dB。**TensorRT-friendly，官方有 ONNX/TensorRT 部署文档**（分类/分割/SAM 应用）。**需重训**。
- **SparseViT**（arXiv:2303.17605）——窗口级激活剪枝，1.3~1.5× 于 3D 检测/实例分割/语义分割，几乎无损；**需 adaptation+搜索+微调**；只适用窗口式 ViT；**无需自定义稀疏核**（窗口天然批量化）。
- **Mamba/SSM 深度**：LMDepth（arXiv:2505.00980）、MambaDepth（arXiv:2406.04532）等——token 线性复杂度，但**无 DA-V2 级预训练权重**，且 SSM 算子在 DML 上的支持未验证。
- **yolo26n/s-depth**（CNN）——T4 TensorRT10 fp16 2.73/3.82ms @768；**但我们已金标裁决「墙缘锐度不足」**；许可证 AGPL-3.0。

**代价模型**：换主干 = 换掉整条已验证链路（含 44 帧金标标定、门/源行参数、回归锁）。成本远高于家族 4/6，收益是**结构性的**（不是常数改进）。

**部署链兼容性**：⚠ **取决于导出与算子**。EfficientViT 有官方 ONNX/TRT 部署路径（最有利）；但 **DML 的 opset≤20、GridSample 5D/DeformConv 不支持、DML 处于 sustained engineering** 三条约束仍适用，且需重新量化（q4f16 未必可得）。**换主干前必须先答「有没有现成的 ONNX + 量化权重」**——否则又是一轮自研导出。

**44 帧金标最小探针**：**不是探针，是立项**。最小前置动作：拿 EfficientViT 的**官方分割/深度权重**（若有）在 44 帧上出图，只看「墙/路台阶的对比度是否优于 DA-V2-S」——若连墙缘锐度都不如现役，直接出局（同 yolo26-depth 的判法）。

### 家族 8：每 token 成本削减（量化 / 蒸馏 / 算子级）

**机制**：网格不变，让同样预算装下更多 token。

**锚怎么保住**：✅ 完全不碰上下文与注意力结构。

**代价模型与现状**：
- **量化**：本目录已走完 fp32 99MB → fp16 49.6MB → int8 26.0MB → **q4f16 19.1MB**；DML 全收、零回退警告；q4f16 无色带、仅平滑低频漂移。**这条轴已被基本榨干**（4-bit 理论下限约 12.4MB，剩余空间有限），且 DML **无 int8 算力路径**（量化图走 dequant→fp 计算）——**再往下压位宽换不到速度**。
- **蒸馏**：把大模型/高分辨率教师蒸馏进小模型。代表：知识蒸馏用于 MDE 的多种框架（TIE-KD arXiv:2402.14340 等）。**需训练基建**（当前没有）。这是「直接训一个更好的小模型」路线，理论收益最干净（可同时改分辨率与位宽），但**成本最高**。
- **算子级**：折叠已是官方口径的终点（free-dim override 三 dim 全固定 → 整图融单节点）；DML 无 CUDA graph 类开关。**剩余空间只剩后处理**（已向量化，observe 合计 26.4ms，其中 infer 16.8ms）。

**部署链兼容性**：✅ 量化/折叠全部已验证；蒸馏产出的是新权重文件，路径同构。

**44 帧金标最小探针**：已有。**唯一建议**：把「位宽」纳入任何提分辨率方案的**必跑对照**（见 §1.2 L4 的推论）。

### 家族 9：解码器侧省而编码器不省（负面结果）

**机制**：保持主干，砍 DPT 头的算力。

**结论：对本任务**无精度收益**，不建议。**
- 依据（§〇 事实 B）：头的空间格点在 @336 已细到输入/3.5（≈7.5px），远细于 token 网格（30.5px）；头不产生新信息，只放大主干 token 网格的信息。
- 头的算力相对注意力**可忽略**（既有记录）；省它换不到预算。
- 「主干低分辨率 + 头高分辨率」在 DPT 类模型**不成立**——主干分辨率才是天花板。

**唯一有价值的变体**：把「头」换成一个**吃高分辨率 RGB 的细化头**——但那已经是家族 6，不是「省」，是「加」。

## 三、部署链天堑：ONNX + DirectML + 静态形状折叠

### 3.1 我们这条链的四条硬约束（内部已验 + 官方文档）

1. **三自由维全固定是折叠的必要条件**：只固定 height/width 而留 batch 符号化，图**完全不变**（节点数、Resize 耗时都不动）。折叠后整图融为单 DML 节点（550→1 个 Node 事件），固定开销地板 2.6ms；不折叠则 cubic Resize（`interpolate_pos_encoding`）回到关键路径，@336 从 19.9ms 变 133.1ms。**漏折叠的形态是「能跑但慢 6 倍」，功能测试全绿拦不住，只有形状锁能拦**（`test_load_session_is_folded_static_shape`）。
2. **DML EP 官方约束**：不支持 memory pattern 优化与并行执行；会话须 `ORT_SEQUENTIAL`；同一 session 只允许单线程串行 `Run`；**只支持到 opset 20**（GridSample 5D、DeformConv 不支持）；DML 进入 **sustained engineering**（新特性转 WinML）——**不要期待 DML 侧后续性能红利**。
3. **动态 shape 的代价是「击穿折叠」**——一次性损失约 6×（@336 档 250.5→39.8ms 为 fp32 口径；q4f16 生产口径 133.1→19.9ms）。**动态 token 数 = 动态 shape = 折叠失效。**
4. **DML 的 Int64 索引雷区（新发现，关键）**：ORT issue **#27118**（2026-01 报告，ORT 1.23.0，Windows 10/11，NVIDIA/Intel 后端无关）：
   - D-FINE / RT-DETR 类 Transformer 模型在 DML 上**初始化或执行即崩** `E_INVALIDARG (80070057)`；**根因 = DirectML 不兼容 `Gather` / `ScatterND` / `TopK` / `NonZero` 的 Int64 索引**。
   - **不能全局 Int64→Int32 降位**：`Reshape` / `Resize` / `Expand` 的 shape/scales 输入按 ONNX spec **强制要求 Int64**，降位直接 `InvalidGraph`。
   - **选择性打补丁会死锁**：PyTorch 导出的动态 shape 计算链是 `Shape → Gather → Concat → Reshape`，同一张量**必须**同时是 Int64（给 Reshape）和 Int32（给 Gather），插 Cast 会破坏常量折叠与形状推断。
   - 报告中该 issue 状态为**未解决**（请求 DML 团队原生支持或加自动降位 pass）。

| 2 固定空间合并表 | ✅ 编译期常量 | ⚠ 未验证（可能打破单节点融合） | ⚠ 仍有 Gather/Scatter | **理论可行，需算子级探针** |
| 3 跨帧门控/复用 | ❌ 掩码逐帧变 | ❌ | ❌ | **天堑**（除非掩码固定→退化） |
| 4 非均匀重采样 | ✅✅ 不改图 | ✅✅ | ✅✅ 无关 | **零部署风险**，风险全在质量 |

| 9 解码器侧 | — | — | — | **无精度收益，关闭** |

### 3.3 「固定合并进度表」这个工程解法的真实边界

用户提出的「固定合并进度表」确实能救回**静态形状**与**折叠**两条约束——因为每层的 token 数是编译期常量，ONNX 图仍然全静态，三个 free dim 仍可固定。

**但它救不了第三条**：合并的实现仍需 `Gather`/`Scatter` 类索引算子，正落在 §3.1-4 的 Int64 雷区。**所以固定表方案的可行性，完全押在「DML 能否吃下静态 Int32 索引的 gather/scatter」这一个未验证的算子问题上**。这也解释了为什么 ToMe 的 ONNX 导出在官方 repo 里仍是 open issue——**问题不在 token 数动态，在索引算子本身**。

**因此建议的探针顺序**（成本从低到高）：
1. **算子级最小探针**（小时级）：手搓一个含 `Gather`（静态 Int32 索引）+ `ScatterND` 的最小 ONNX 图，在 DML 上起会话并 Run。**这一步的结论决定家族 1/2/3/5 是「需工程」还是「直接关闭」。**
2. 若算子可过，再测「插入合并后折叠是否仍是单节点」（看 Node 事件数与 p50 对 2.6ms 地板）。
3. 只有前两步都过，家族 2 才值得投离线质量探针。

## 六、建议的探针顺序（成本从低到高，全部可在 44 帧金标上离线做）

**第 0 步（必做，小时级，决定半张地图）**：**DML 静态 Int32 索引算子探针**——手搓含 `Gather`/`ScatterND` 的最小 ONNX 图，在 DML 上起会话 + Run。这一步的结论决定家族 1/2/3/5 是「需工程」还是「直接关闭」，且**不依赖任何模型改动**。

**第 1 步（性价比最高，一天级，零部署风险）**：**家族 4 的非均匀重采样探针**。固定一条垂直分段线性映射，用现有折叠会话跑 44 帧金标，比 dev/覆盖率/双侧同现 vs 全帧@336 与 @448 两个参照。判据见家族 4。

**第 2 步（并列最高，一天级，零部署风险）**：**家族 6 的经典 guided filter 探针**。@336 折叠输出 + 全分辨率 RGB → guided filter 上采样 → 比 dev/覆盖率，**并统计污染带内的伪台阶数**（texture copying 代价）。若滤波类不达标再评估 NAIMA 式语义门控。

**第 3 步（先验统计，半天级）**：**家族 3 的前置问题**——本域 ~20Hz 相邻帧的 token 变化比例。若 >50%，家族 3 直接关闭，省下整条线的调查。

**第 4 步（仅在第 0 步通过后）**：**家族 2 的离线正确性探针**（@448 + 固定顶部合并表 vs @336/@448 参照），通过后再做 ONNX 折叠节点数探针。

**第 5 步（只在 1~4 都出局时）**：家族 7 的立项评估（先答「有无现成 ONNX + 量化权重」）。

**所有步骤的统一前置**：晕影治理（门 0.08 已在生产；per-side 门与晕影模板扣除是候选）。**在晕影幅度（±3~6% 视差）未被压到目标台阶量级以下之前，任何精度探针的结论都要在「晕影掩码外的子区域」上读**，否则无法把机制的贡献与污染分开。

## 七、旁支决策：要不要换模型（DA3 / 时序架构）

**问题**：我们有大量连续运动帧；如果另一个架构能「容易地」同时做到高效高质，就不在 V2 上缝缝补补了。**结论：不建议换；且 DA3 严格来说不是「别的架构」。**

### 7.1 DA3 没有换架构，只是把同一结构做大

【官方文档】DA3 项目主页与论文摘要的原话：

> 「**No complex tasks! No special architecture!** just a single, plain transformer trained with a depth-ray representation.」
> 「a single plain transformer (e.g., **vanilla DINO encoder**) is sufficient as a backbone without architectural specialization」

【官方源码/README】backbone = DINOv2，head = **DualDPT**；主系列支持 N=1 的单图单目推理。

⇒ **DA3 = DINOv2 + DPT 的同一家族**，与我们现用的 DA-V2-S（DINOv2 ViT-S/14 + DPT）**同构**。本文 §〇 事实 A（均匀 patch 下 token 数 ≡ 空间采样密度）与事实 B（DPT 头格点不是瓶颈）在 DA3 上**原样成立**——它继承完全相同的均匀 patch 划分与 O(N²) 全局注意力，**不改变任何结构性约束**。

**尺寸与许可证（【官方模型表】）**：

| 档 | 参数量 | 相对 DA-V2-S(24.8M) | 许可证 | 能否对标本任务 |
|---|---|---|---|---|
| DA3-SMALL（any-view 主系列） | 0.08B = 80M | **3.2×** | Apache-2.0 ✅ | 可商用，但非专用单目相对深度 |
| DA3-BASE | 0.12B = 120M | 4.8× | Apache-2.0 ✅ | 同上 |
| **DA3MONO-LARGE**（专用相对单目深度） | 0.35B = 350M | **14×** | Apache-2.0 ✅ | **唯一对口的档，但 14× 规模** |
| DA3-LARGE / GIANT / NESTED | 0.35B / 1.15B / 1.40B | 14×~56× | **CC BY-NC 4.0 ❌ 不可商用** | 出局 |

**精度声称的强度**（【论文摘要】）：DA3 自述「achieves a level of detail and generalization **on par with** Depth Anything 2」，并「outperforms DA2 in monocular depth estimation」。**即细节持平、单目指标更好——是量级内的进步，不是跃升**，而代价是 3.2×~14× 的规模。

### 7.2 当前瓶颈不在模型上——换药治不了病

09-24 实机复核已把三件事**分别**钉死（详见本目录 README「实机复核」节）：

| 症状 | 真根因 | 换深度模型能解决吗 |
|---|---|---|
| 覆盖率低 | **读数带里没有边**——金标边界线 R 51/54、L 28/54 帧在 y<550 出画；生产带 550~700 整行皆路面 | ❌ 不能 |
| 精度被拉偏 | **自车邻近晕影**（±3~6% 视差，横向溢出 150~250px） | ❌ 不能 |
| R 侧读不出 | 弱台阶（墙侧本底 +4.4% 贴门） | ⚠ 部分可能，但先修门/晕影更便宜 |

而**边界真在画面内且过守卫的帧精度本来就良好**（L 接受 14 帧、dev 中位 −5px、p90 13px）。实机复核的原话是「**几何没错，错的是读哪一行和每拍成本**」。这三条没有一条是「模型看得不够好」。

### 7.3 「连续运动帧」的钱我们已经在捡，且时序一致性不是我们的痛点

- **消费侧已经在用**：异步 latest-only + **每侧独立保鲜槽**（~400ms ≈ 8 拍），把「同帧双侧 18%」摊成「每侧 ~90%」。**零模型改动**——这是最便宜的时序利用形态。
- **DA-V2-S 的帧间稳定性本来就够**：相邻帧近区掩码 IoU 中位 **0.968**（p10 0.827）。**时序模型最大的卖点是「不闪烁」，而我们不闪**——所以那个卖点买不到东西。
- **时序模型的真实代价（【官方 README/项目页】）**：
  - **Video-Depth-Anything**：7.5ms / **32 帧**（FP16，A100，1×32×518×518）——单帧成本 ×32 摊销，需**序列输入**（静态形状更难），**无官方 ONNX**；社区有 TRT 引擎（ruffy369）与 ONNX C++ 实现（ZInkzach），均非官方。
  - **DA3-Streaming**：**8.51 FPS @~500px 宽、A100、峰值显存 15.9GB**（KITTI 504×154，chunk=120）。它输出**相机位姿 / 内参 / 点云**——是**里程计/SLAM 管线**，不是「读深度」的形态。**比我们 4060 Laptop 上折叠 @518 的 90.8ms（11 FPS）还慢**，且显存远超消费级。
- **判据回归**：延迟已异步化 ⇒ 方案价值只能在「**同等代价下读数质量上限**」这一轴找。时序架构买的是**一致性**与**更新率**，两样我们都不缺。

### 7.4 我们的「高效」不是架构给的，是工程链给的

现有高效来自三件**已在本机验证**的事：

1. **官方量化 ONNX 导出**——onnx-community 全套（q4f16 **19.1MB**，Apache-2.0，无色带）；
2. **DML 全收零回退**——全部量化变体在 DML 上无 EP 回退警告；
3. **三自由维折叠**——整图融为单 DML 节点，@336 从 133.1ms → **19.9ms（6.3×）**，且折叠形状锁进回归测试。

**DA3 的部署生态现状（【检索】）**：**无官方 ONNX、无官方量化**；只有社区导出（SpatialHub/depth-anything-3-onnx、zerochocobo/DepthAnything3_ONNX、devin-lai/Depth-Anything-3-Onnx，均未见过量化版本），TRT 只有第三方 ROS2 包装。依赖里有 **xformers**（对旧 GPU 不友好）。

⇒ 换过去要**重建整条链**：导出 → 折叠验证 → 量化选型 → DML 算子合规（含 §3.1-4 的 Int64 索引雷区）→ 44 帧金标重标 → 门/源行重定 → 回归锁。**而收益侧只是「细节持平」。**

### 7.5 什么时候才该换——可证伪的触发条件

现在不换**不是**因为「在 V2 上缝缝补补更好」，而是因为**诊断还没走完**。项目自己列的下一轮顺序是：①观测器离开控制拍热路径 → ②读数带按「边界在画面内的行」重定。这两步落地后，**三条同时成立**才说明模型是瓶颈：

1. 晕影已治理（门 0.08 已在生产；per-side 门 / 晕影模板扣除为候选），且
2. 读数带已按「边界在画面内的行」重定（禁止固定 [550,700]），且
3. L 侧 @336 的 dev p90 与覆盖率**仍然**显著劣于离线质量上限（DA-V2-B / @518 这类**不可发布的参照档**），**且该差异能归因到深度质量本身而非几何/管线**。

**在这三条之前谈换模型，等于在没诊断清楚前换药。**

### 7.6 真要换，该换的不是 DA3，是「能改变成本-分辨率曲线」的那一类

能真正改变曲线的架构替换（本文家族 7）：**线性注意力**（EfficientViT——官方有 ONNX/TensorRT 部署路径，最有利）、**窗口/稀疏注意力**（Swin + SparseViT）、**SSM**（LMDepth / MambaDepth）。它们才是「别的架构」。

但现状是：**均无 DA-V2 级预训练深度权重、无可用的量化 ONNX**（EfficientViT 官方应用清单为分类/分割/SAM，未列深度）⇒ 属重训 + 重导出的大工程，且收益不确定。

**双向结论**：**DA3 不值得换**（同架构、更大、无部署生态）；**真正值得换的那一类现在还不可用**。

### 7.7 唯一值得给 DA3 留的位置

**离线质量天花板参照**：DA3MONO-LARGE（0.35B，Apache-2.0，专门的相对单目深度模型）可作「不可发布的质量上限」离线对照——与现在用 DA-V2-B 的角色相同。**但这不改变生产选型。**

## 八、一句话总结

336→518 的钱花在**编码器 token 网格**上（30.5px→19.7px 采样密度）与**全局注意力的样本量**上；DPT 头的空间格点两档都已细 4 倍，**不是瓶颈**；量化地板是第三个轴、当前未绑定但会被提分辨率激活。在均匀 patch 的 ViT 里，**token 数 ≡ 空间采样密度**，打破它只有三条路：重分配 token、换信号补定位、削每 token 成本。而本任务要的是一根**线**而非一张图，逐行噪声被拟合平均掉 ⇒ **绑定精度的是系统性偏置（晕影、弱台阶），不是分辨率**。落到部署链上，**所有以 token 索引为核心的家族（1/3/5）都撞在同一条天堑上：DirectML 对 Int64 索引算子崩溃，且动态 token 数会击穿折叠（6× 代价）**；真正零部署风险的两条是**家族 4（非均匀重采样，纯 preprocess）与家族 6（跨模态引导细化，卷积原生）**——它们恰好也是唯二「锚天然不动」的家族。
