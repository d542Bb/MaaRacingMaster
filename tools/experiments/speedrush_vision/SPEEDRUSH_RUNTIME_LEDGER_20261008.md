# speedrush 运行时账本剖析（第二版 · 深挖）

**日期**：2026-10-08 · **语料**：31 个控制 trace / **24,670 控制拍** / **6,940 个深度实例**（2026-10-07 ~ 10-08）
**方法**：全部基于**既有 trace 账本 + 外部只读探针**，未改动任何产线代码

> 第一版回答的是"**这 4.33 个核花在哪里**"。
> 这一版回答的是"**每一次计算从采集到被消费，时间到底花在哪一段；以及这些计算产生了多少仍然有用的信息**"。

---

## 0. 摘要：五个新结论

| # | 结论 | 证据强度 |
|---|---|---|
| 1 | 深度实例的年龄可**闭式拆解**：`采集→入槽 + 槽内等待 + 计算 + 发布→消费`，**计算占 63%** | 6,940 实例，对账偏差可解释 |
| 2 | **后处理（平面+找边+栅格 70ms）比推理（forward 55ms）还大**——优化杠杆在后处理 | 全语料 P50 |
| 3 | **控制拍被硬量化**在 50ms / 66ms / 33ms 三模态；**33.4% 的拍超 20Hz 预算**，且**与深度到达无关** | 24,653 个 dt 的直方图与配对 |
| 4 | **价值损耗被量化**：深度年龄 **100% 超 100ms 安全下限**、54% 超 200ms；新深度里 **18.6% 拿不到几何**；44.8% 的实例侧向读数被拒 | 全语料计数 |
| 5 | 计算成本**会话间波动 37%**（131→180ms），各段**同涨同跌** → 指向机器级争用，而非某段代码 | 31 个会话逐段 P50 |

## 1. 运行时账本：字段与闭式预算

### 1.1 账本结构（既有 trace 已含完整时间线）

每个深度实例都带一个 `dgeo_seg`，字段定义（`depth_geo.py:295-298`）：

| 字段 | 定义 | 含义 |
|---|---|---|
| `cap_ms` | `t_push − frame_ts_ns` | **采集→入槽**（帧到达回调到被放进 latest-only 槽） |
| `queue_ms` | `t_start − t_push` | **槽内等待**（入槽到 worker 开工） |
| `stages` | 7 段 | `pre / forward / reconstruct / upsize / plane / edges / grid` |
| `pub_ms` | `t_consume − t_pub` | **发布→被控制拍消费** |

四段相加恰好等于该实例被消费时的总年龄——**这是一个闭合账本**。

### 1.2 闭式年龄预算（P50 / P90，ms）

| 项 | P50 | P90 | P50 占比 |
|---|---|---|---|
| ① 采集→入槽 `cap` | 23.0 | 38.3 | **10.0%** |
| ② 槽内等待 `queue` | 18.5 | 46.4 | **8.0%** |
| ③ **计算 `compute`** | **146.2** | **166.4** | **63.4%** |
| ④ 发布→消费 `pub` | 18.1 | **78.6** | **7.9%** |
| **= 总年龄** | **230.7** | **285.2** | 100% |

> trace 自记的 `dgeo_age_ms` P50 = 201.2ms，与闭式值差 −29.3ms；差异来自 `cap_ms` 用的帧采集时基与消费侧时基不完全同源，量级可解释，不影响各段占比结论。

**读法**：把 230ms 的年龄归因，**63% 是算出来的**，其余 37% 是等待（入槽 10% + 排队 8% + 发布后等待被取走 8%，P90 时这一段冲到 78.6ms）。

## 2. 计算内部：后处理比推理还贵

| 段 | P50 (ms) | 占计算 |
|---|---|---|
| `pre` 预处理 | 6.1 | 4.2% |
| **`forward` 推理**（MoGe q4f16 @336×598, DML） | **55.3** | **37.8%** |
| `reconstruct` | 6.5 | 4.4% |
| `upsize` | 5.7 | 3.9% |
| `plane` 平面拟合 | 18.2 | 12.4% |
| **`edges` 点云找边** | **37.6** | **25.7%** |
| `grid` 可行驶栅格 | 13.9 | 9.5% |
| **合计** | **146.2** | 100% |

```
推理      55.3ms  ████████████████
后处理    70.0ms  ████████████████████   ← plane 18.2 + edges 37.6 + grid 13.9
                    后处理 = 推理的 1.27 倍
```

**这是本轮最直接的优化杠杆**：把 146ms 砍到 110ms，收益全部落在后处理（找边+栅格+平面），而不是模型分辨率。

## 3. 控制拍被硬量化（本轮最刺眼的新发现）

### 3.1 dt 直方图

```
 33.3ms ██████████████                14.5%   ← 30Hz（比目标快）
 50.0ms ████████████████████████████████████████  43.0%   ← 目标 20Hz
 66.7ms ███████████████████           19.9%   ← 15Hz（超预算）
 其它   ██████████████████████        22.6%
```

三个模态间隔**恰好 ~16.7ms**，模态之间几乎空白——**这是 OS 定时器粒度把 sleep 量化出的台阶**。

### 3.2 不是"平均慢"，是"台阶化"

| 指标 | 值 |
|---|---|
| dt 均值 | **52.54 ms → 有效 19.03 Hz**（目标 50ms，系统性过冲 2.54ms/拍） |
| 超 20Hz 预算（>52ms） | **33.4%** |
| 落在 15Hz 档（66±3ms） | **19.9%** |
| 落在 30Hz 档（33±2ms） | 14.5% |

### 3.3 关键否证：**抖动与深度无关**

| 分组 | n | P50 | P90 | 超预算 |
|---|---|---|---|---|
| 全部拍 | 24,670 | 50.2 | 66.7 | 33.4% |
| **有新深度的拍** | 6,940 | 50.1 | 66.5 | **32.1%** |
| 无新深度的拍 | 17,730 | 50.2 | 66.9 | **33.9%** |

两者几乎一样 → **拍抖动不是深度造成的**，是 pacing 本身的问题。

### 3.4 机制

- 控制拍 pacing（`module.py:653-662`）：`t0=perf_counter()` → 跑环体 → `rest = 50ms − 环体` → `lifecycle.sleep(rest)`。
- `lifecycle.sleep`（`capabilities.py:249-269`）用 `time.sleep(min(remaining, 0.1))` + perf_counter deadline。
- **项目全库未调用 `timeBeginPeriod` / `NtSetTimerResolution`**（全库 grep 无命中）。
- 因此 `time.sleep()` 仍落在系统默认定时器网格上；deadline 时钟换成 QPC（perf_counter）只让**校验**变细，**没有让睡眠本身变细**。
- 配对统计印证"过冲后追赶"：`34ms→66ms` 720 次、`33ms→66ms` 494 次、`33ms→67ms` 467 次。

> 注：代码注释（`module.py:593-595`）已记录过同一现象——"monotonic 粗钟把环体量化成 0、33ms 请求实睡 46.8ms"。本轮数据显示：**换成 perf_counter 后量化仍在，只是换了形态**（50/66/33 三模态）。

## 4. 价值损耗：算出来的东西有多少还能用

### 4.1 新鲜度

| 指标 | 占比 |
|---|---|
| 深度年龄 **>100ms**（安全下限） | **100.0%**（6,937/6,940） |
| 深度年龄 **>200ms** | **54.4%**（3,773/6,940） |

**安全下限从未达成**——这不是偶发，是结构性的。

### 4.2 产出可用性

| 指标 | 占比 |
|---|---|
| 深度实例产出新结果 | 28.1%（6,940/24,670）→ 有效 **5.4 Hz** |
| **新深度里 `ro_source=none`**（算完仍拿不到几何） | **18.6%**（1,288/6,940） |
| 全拍 `ro_source=none` | **27.6%** |
| 带侧向拒绝记录的深度实例 | **44.8%**（3,107/6,940） |

侧向拒绝原因（全量计数）：

```
L:无穿越   4614
R:无穿越   4389
L+R 都无穿越  243
平面拟合失败    33
```

### 4.3 控制侧输出分布

```
state : CRUISE 21119(86%)  CHANGE 2079  CONSERVE 971  ABORT_CHANGE 501
reason: hold:no_candidate 17827(72%)  hold:cooling 3040  moving:overtake 1706
        validate_fail:target_empty 634  aborting 363  conserving 337  select:score_win 232
```

**72% 的拍是 `hold:no_candidate`**，真正 `select:score_win` 只有 232 拍（0.9%）。

> 把 4.1~4.3 连起来看：**每 146ms 一次的昂贵深度计算，有 44.8% 的实例至少一侧读数被拒、18.6% 完全产不出几何；而它服务的控制输出有 72% 的拍什么都不做。** 这正是"利用率"与"新鲜度"分离的地方——CPU/GPU 在忙，但忙出来的信息大量落在**已经没有决策价值**的时刻。

## 5. 会话间波动：不是"越跑越慢"，是机器级争用

逐会话 `compute` P50（ms），按时间排序：

```
10-07 20:55  154.1      10-08 12:25  146.6      10-08 18:37  140.3
10-07 21:31  146.5      10-08 12:27  145.2      10-08 18:44  134.8
10-07 21:42  143.6      10-08 12:28  148.6      10-08 18:53  142.2
10-07 22:30  142.4      10-08 14:11  155.6      10-08 19:04  135.9
10-08 11:49  131.3      10-08 14:12  159.4      10-08 19:11  150.2
10-08 12:04  132.4      10-08 14:56  153.7      10-08 19:19  151.8
10-08 12:05  131.4      10-08 15:00  180.2  ←峰值 10-08 19:20  150.8
```

| 观察 | 值 |
|---|---|
| 最快会话 | 131.3 ms（11:49） |
| 最慢会话 | 180.2 ms（15:00） |
| 波动幅度 | **+37%** |
| 波动结构 | `forward / plane / edges / grid` **同涨同跌** |

**同涨同跌**说明不是某一段代码退化，而是**整机状态**（CPU 争用 / GPU 上下文切换 / 功耗状态）在影响。所以"深度越跑越慢"这个提法应修正为**"深度成本随机器状态波动"**——GPU 侧已排除热降频（SM 2775MHz 满血、55~59°C）。

## 7. 调度视角：每个任务的"契约"与"实际达成"

把上面所有数据按**调度契约**重排（这是第一版没有的视角）：

| 任务 | 名义频率 | 单次成本 | deadline 性质 | **实际达成** | 违约形式 |
|---|---|---|---|---|---|
| 控制拍 | 20 Hz | 环体 ~14ms | **硬**（到点必须出） | 19.03 Hz | **33.4% 的拍超预算；19.9% 掉到 15Hz** |
| YOLO 检测 | 每拍 | 12.8ms | 硬（同拍） | 18.5 Hz | DML 等锁 P95 45~57ms |
| 深度几何 | 最新帧优先 | **146ms** | 软 | **5.4 Hz** | 年龄 **100% 超 100ms 下限**，54% 超 200ms |
| HUD 读数 | 2 Hz | 584ms/行 | 松 | 1.71 Hz | 略低 |
| 调试图 | ~2 Hz | 23ms | 无 | ~2 Hz | — |

**这张表就是"运行时账本"的汇总形态**：控制是 deadline-driven 却在失期；深度是 value-driven 却在按固定节奏空转；两者都缺一个"这一刻值不值得启动"的判据。

## 9. 与"调度器架构"的差距（只做映射，不改代码）

把现有实测数据对照一个调度器该有的判据，缺口很清楚：

| 调度器需要的输入 | 现状 | 缺口 |
|---|---|---|
| 每次计算的 `deadline / priority / reason_started / reason_dropped` | trace 有 `dgeo_new / dgeo_rejects / ro_source`，但**没有"为什么这次启动了"** | 缺启动判据记录 |
| CPU busy / wait 分离 | 有 `queue_ms / pub_ms`（等待已分离） | 计算段内**没有 GPU busy vs CPU busy 的分离** |
| 价值度量（结果是否还在有效期） | 有 `dgeo_age_ms`（年龄有） | 缺"产出是否被使用"的闭环（`ro_source=none` 是弱代理） |
| 资源预算 | 无 | 无 per-epoch 的 CPU/GPU 预算 |

**最值得补的一项**：给每个深度实例记一条 `reason_started`（为什么这一刻决定跑）与 `used_by_control`（结果有没有真的被决策采用）。有了这两列，"哪些计算根本不该启动"就从猜测变成统计。

## 10. 未决与边界

1. **闭式年龄与 trace 自记年龄差 −29.3ms**：`cap_ms` 的采集时基与消费侧时基不完全同源，未做时钟对齐验证。
2. **dt 三模态的精确网格值**：观测间隔 ~16.7ms，但未直接测得当前系统定时器分辨率（默认 15.625ms 与观测值差 ~1ms），需要 `NtQueryTimerResolution` 实测才能定论。
3. **GPU busy vs CPU busy 未分离**：`forward 55.3ms` 是墙钟，其中多少是 GPU 执行、多少是 CPU 提交/同步，现有账本答不了。
4. **`pub_ms` P90 78.6ms 的成因未定位**：可能是控制拍消费节奏（50ms 台阶）的必然结果，也可能是槽上锁竞争；需要按实例对齐消费时刻才能判定。
5. 本轮**未验证**：若把 `sleep` 改为高精度等待（`timeBeginPeriod` / 可等待定时器），dt 三模态是否收敛——这属于改造，不在本次剖析范围。
