# frame_delta — 路心/执行位帧差与参考系分账（活跃）

status: active

**问题**：生产计划在「场景路心位置」与「执行位」差超过 1 m 时整拍失效
（`plan:frame_shift`）。本实验只读地量化：大差窗口由哪类路心来源产生、哪些
窗口确实关联计划否决/换道中断、能否定位到具体数据源或接口边界。

**只读**：不 import 控制链、不改生产数据；只读 trace 与 policy JSON。

## 运行

```bash
.venv/Scripts/python.exe tools/experiments/frame_delta/probe_frame_delta.py \
    [--manual 20261028_225902] [--session NAME ...] [--root DIR] [--selftest]
```

默认读 `%APPDATA%/MaaRacingMaster/logs/*/trace/speedrush.jsonl`；`--manual`
把指定会话标为人工局（trace 里没有驾驶模式字段）。

## 口径

1. **帧差** `fd`（米）：优先 `plan.fd`（生产同一量）；无计划但有场景时用
   `scene.ego_m - executed_lane*lane_w` 重建；缺任一侧记未知。
2. **大差**：`|fd| > motion.frame_delta_hold_m`（当前 policy = 1.0 m）。
3. **窗口**：相邻大差拍**最多夹 1 拍**非大差（桥拍）即并入；夹 ≥2 拍断开；
   `fd` 未知拍断开并单列（不冒充非大差拍）。
4. **来源**：`ro_source` × `dgeo_new`（本拍是否有新深度）× `ro_hold`
   （planner 是否按历史保持消费）。窗口同时记首拍来源、主导来源与切换史；
   不按结束来源归类。
5. **计划**：`none`（未生成）/ `veto`（生成后被否，按 reason）/ `valid`，
   前两者分开计数。
6. **冻结中心**：窗口内同一 `road_offset` 连续 ≥3 拍、且执行位移动 >0.3 道。
7. **重基事件**：`lat_ctrl.rebase` 非空的拍；exec 跳变 = 本拍 executed 与
   上一拍之差。
8. **线观测只作辅助**：`lane_fuse.trusted` 且 `sm` 非空时比较
   `|road-sm|` 与 `|exec-sm|`；线也参与 executed 融合，不是独立裁判。

## 首轮结果（7 局：6 程序 + 1 人工，11,506 拍）

- 大差拍 2,856（24.8%）；窗口 661；**大差且计划有效 = 0**，与「帧差异否」
  是同一个量的机械关系，不是独立发现。
- 非大差但被否 100 拍：99 拍 `infeasible_corridor`、1 拍 `frame_shift`
  （阈值舍入边界）。

- 具体样例（`20261028_210938` fid 4029–4138，54 拍 / 2.7 s）：wall_occl/
  memory 保持的路心卡在 −1.6 道，车实际从 +0.49 移到 +0.20；重基前帧差从
  −2.8 涨到 −6.2（4060 拍）；4062 拍 `hold_stale` 重基把 executed 从 +0.197
  一步拽到 −1.637（1.83 道）；4064 拍路线换纪（ref 0→−1），并线被结束；
  窗口尾部参考系再跳，fd 翻到 +6.5。
  这条链是**重基修正 → 执行位大跳 → 路线换纪 → 承诺作废**，不是选择器选错。

## 三问的回答

1. **哪类来源产生大差窗口**：wall_occl 与 wall 各占 40%（各 264 个首拍）；
   按主导来源 wall_occl 49%。wall_occl/memory 合计约 50%——**保持读数是
   半壁江山**；wall 是新深度跳变。共同点是来源交接，而不是单一算法。
2. **哪些窗口导致计划否决/换道中断**：所有窗口都机械地触发帧差异否（同一
   个量）；26% 窗口与并线重叠；并线结局前 10 拍有窗口 64% vs 基线 50%，
   **关联弱**。真正锐利的是重基：94 次里 85 次跟着换纪。
3. **能否定位到数据源/接口边界**：能定位到**参考系交接与重基/换纪的接口**：
   - 窗口首拍 90% 在来源/状态切换的 2 拍内（基线 62%/68%）；
   - 冻结中心窗口 124 个（19%），wall_occl/memory 占大头；
   - 重基把路心修正写成约 1 道的执行位跳变，路线换纪门（0.5 道）随即作废
     承诺——**修正与换纪在互相打架**。
   - 线观测更像支持执行位（79%），但线参与执行位融合，只能当线索，不能
     据此判「路心算法错」。

## 结论与边界

- **已确认**：大差 = 计划整拍失效（25% 拍）；窗口集中在来源交接；重基修正
  与路线换纪形成高频链路（85/94），单次约 1 道执行位跳变。
- **未确认**：大差是否导致大部分换道中断（基准校正后关联弱）；是否是选择
  目标错（ref 只变 7.4%）；哪一侧估计器真的错（线不独立）。因此不能把
  「开得不好」直接归因到路心算法。
- **失败形态更像**「修正把承诺冲掉、计划被拿掉」，而不是「选错道」。它对
  得分/安全的影响还需要单独的度量（计划失效期间的避让/贴线表现）。
- 人工局与程序局：大差拍占比相近（21% vs 25%），但重基 5 vs 89——差异在
  **修正响应**，不在失配发生率；赛道不同，不能当因果。
