# speedrush_depth_update — 深度结果"更新时长"压进目标窗口（验证与停止清单）

> **本实验要回答的唯一问题**：当前深度感知调度到底有没有在损害得分？如果有，哪一个边界值得动？
> 回答完这两个问题就停止取证、进改造——**这是验证与停止清单，不是下一步技术方案。**
> 信源等级 L4（过程与证据）。结论兑现后按 [tools/experiments/README.md](../README.md) 生命周期四步退役。

## 目标（用户定，肯定项）

把深度结果从「帧采集」到「被控制拍消费」的**更新时长（age）缩短到稳定压进目标更新率窗口**
（时效预算 `MAX_AGE_MS=350ms`，复用上限；深度目标节奏约 8Hz→周期 ~125ms）。

## G1/G2 — 既有 trace 的生命周期拆分

用户提供的四局 `dgeo_seg` 汇总将年龄拆为互斥区间（单位 ms）。该汇总并非当前实验目录的产物；原 trace 未随实验材料落盘，因此这里保留其来源边界，不把它写成此次独立复算。

| 区间 | p50 | p95 | max | 是否占 DML 锁 | 解释 |
|---|---:|---:|---:|---|---|
| cap（采集→入队） | 26 | 62 | 112 | 否 | 含等待 YOLO 检测 |
| queue（入队→开工） | 20 | 45 | 130 | 否 | 节流窗等待 |
| forward（DML 前向） | 54 | 62 | 141 | **是** | 唯一锁内核 |
| post（前向后 CPU 处理） | 41 | 54 | 160 | 否 | edges 与 grid 已并行 |
| pub（发布→控制拍消费） | 68 | 86 | 166 | 否 | 控制线程采样节拍造成的驻留时间 |
| **age 合计** | **210** | **269** | **348** | | p50 接近但低于约 350ms 年龄闸 |

区间按帧相加后与 age 闭合，Σ误差 p50=0.0ms。各区间的分位数和最大值来自各自分布，不能把不同列的分位数相加来重建 age 的同分位数。

`pub` 不是生产者在等发布：worker 算完即将同一帧读数与栅格整包写入驻留槽；控制线程约每 47ms 采样一次，直到下一拍才拿到新内容。两次采样之间，`take()` 继续返回上一份完整驻留结果，因此这段时间不会让控制器停下来。锁边界由 [depth_geo.py](../../../maaracing_master/plugins/speedrush/depth_geo.py#L413-L427) 的非阻塞 acquire、前向调用及 finally release 确认，后处理在释放锁后执行。

**当前可确定的延迟构成**：cap、queue、pub 是等待区间，post 是 CPU 处理，forward 是 DML 锁内原子段。单看这些 p50 不足以证明节流、YOLO 等待、控制节拍或年龄闸可以安全调整。

### 只读范围检查 — 可疑的重复唤醒

worker 在节流窗内等待时，每次新帧入队都会唤醒它；它重新计算同一个开工期限后继续等待。期限内的 pending 帧会被新帧覆盖，退出/停止也有单独唤醒。因此，节流窗内的入队唤醒看起来不改变选帧或控制结果，可能只增加 worker 醒来与重算等待的次数。当前 trace 不记录唤醒次数或这部分 CPU 成本，预期收益尚不能量化；保留为唯一值得小范围验证的候选，**本次不改生产行为**。若要确认，最小验证是给 worker 做短时只读计数，或微基准比较节流窗内唤醒次数与 CPU 时间；只有收益清楚后再考虑改动。

## 四个验收门（每项拿到证据才算过；拿不到就按停止条件放弃该路线）

### G1 — 锁行为
- 证据：真实 acquire→release 连续占锁时长分布（含尾），与 `forward_ms` 对齐。
- 不通过含义：若真实占锁 ≠ forward_ms（锁在 pre/forward 间被放开或有偏移），切片收益估算作废。

### G2 — 结果生命周期
- **状态：已由既有 trace 汇总回答。** 五个互斥区间与闭合误差见上表；`pub` 对应槽写入后等控制拍采样，不是同步发布阻塞。`take()` 的驻留读取语义意味着消费者在等待新内容期间仍使用上一份完整结果。
- **边界**：当前目录没有保存该批 trace，数值来自用户提供的四局汇总；若要复核原始逐帧闭合，需要恢复那批 trace。无需为更精确数字新增生产埋点。

### G3 — 时间切片可行性（已跑，状态=受阻降级，非封死）
- 已取证据（`probe_moge_time_slice.py` 回放 40 帧 raw）：模型=ViT-S 编码器、1787 节点、24 MatMul、
  **Cast×397**（q4f16 fp16 靠它撑）、无融合 Attention/LayerNorm（被 DML 整图融合）；单次前向 **p50 44.5 / max 53.1ms**。
  沿 `blocks.7` 一个切点 `extract_model` 失败（子图 Cast 依赖跨切点，无法拓扑排序）。
- **边界（勿夸大）**：这只证明**该切点**提不出合法子图，未证明所有 block 边界都提不出。
  其余 block 边界尚未穷举；时间切片因此**降级、不作为主线**。现有结果不足以断言其他边界可行或不可行。
- 不通过含义（保留）：若遍历多数 block 边界均不能保留融合收益 → 停止时间切片路线。

### G4 — 得分归因（离线配对已跑，观察性无关联；真机干预未做）
- **已跑**：110 个旧局 → 阶段二、`hud_rate`（游戏显示得分率）>0 的干净样本 n=139。得分率 vs
  年龄p50 r=−0.01、vs 断供% r=−0.06、vs 新结果% r=−0.03、vs YOLO等待p95 r=+0.03——**全≈0**。
- **自然实验**：断供≤5% 的局中位得分率 41，断供≥12% 的局 41；被堵轻/重两批也一致。即"栅格最饿的局"
  和"几乎不饿的局"打得一样好。
- **判读（勿反向夸大）**：既有分布内（年龄 p50 216–254ms、且驻留语义始终让控制器手上有可用读数）看不出
  新鲜度↔得分关系，**不支持为得分去做流水线改造**。这不等于"新鲜度永不重要"——样本挤在窄区间、
  得分被车流/对手/决策主导（19–785），从未测过"深度真的很差"的区间；要证阈值效应需**故意劣化深度**。
- 触发停止条件 3 → 默认**停止本轮流水线优化**，回路面判断与避障判据。真机单变量对照暂不启动。

## 关键实测结论（本轮探针，2026-11-03）

- **run 时间 vs 分辨率**（`probe_dml_crash_boundary.py --sweep`）：1280×704→49.3ms、960×544→43.1、
  640×352→41.5、480×256→41.6。**像素砍到 1/4 时间几乎不动** → 那 ~40ms 是**每次调用的固定 dispatch 税**
  （1787 节点逐个提交 + 同步），**不是**画面计算量。**降分辨率治不了它**。
- **forward 分段**（同脚本）：`run_with_iobinding`=39.8ms、`copy_outputs_to_cpu`=0.4ms → GPU 完成在 run 内同步等待，
  读回几乎不耗时，**锁无法靠"把读挪出锁"缩小**。
- **DML 崩溃边界**（同脚本 --drive，真并发+计数器+异常捕获）：两会话并发 session.run 时，**后到的 run 报
  ONNXRuntimeError 0x80004005（DmlCommandRecorder / DmlGraphFusionHelper）**；run + 纯 CPU matmul 并发**安全**。
  → 崩因是**两个 GPU run 同时在飞**这一件事，与"锁占多久/CPU 并发"无关。是 ORT-DML 已知并发 bug（#20713），非硬件律。
- **graph capture 正确性**（同脚本 --capture）：`ep.dml.enable_graph_capture=1` 建会话成功，但**第一次
  run_with_iobinding 即段错误崩溃**（exit 139，未产出任何帧）——capture 在当前折叠 q4f16 模型上不可用，
  连"提速/冻结"都谈不上。（与早期 README 记录"capture→163ms、30x 系冻结输入假象"同源：此路不通。）

**DML 内部四条出路逐一实测皆堵**：并发吃空闲=#20713 崩；缩锁=不可能（run 是单个 40ms 阻塞调用、copy 仅 0.4ms）；
降分辨率=无效（run 是分辨率无关的固定 dispatch 税，49→41）；graph capture=首 run 崩。
**剩余唯一能降那 40ms 固定税的 = 减节点（更小骨干，精度代价）或换后端/CUDA（本线排除）。**

**由此 DML 内部剩余空间收窄为两条**（都不换 CUDA）：① 让 graph capture 正确工作（捕获后仍能重绑新帧——
仓库先前 capture 得 163ms 且"30x 是冻结输入的假象"，是正解未做成）；② 减节点（更小骨干，有精度代价）。
并发吃空闲那 50% = 必须绕过 #20713（CUDA/补丁 ORT），本线排除。

## G5 — 错峰排期（2026-11-03 落产线；首轮已跑，修 push 取帧后待复验）

**问题（近 5 局实测）**：前向 54ms 是不可分割的原子、比控制拍 50ms 还长。自由起跑时它伸进
下一拍的余量在 1~54ms 之间随机——37~42% 的拍要等锁；每轮前向压住 1 拍最常见（≈71%）、
2 拍 8~14%、从未 3 拍；被压的拍里等满 40~54ms 与 10ms 以内两档最多、20~40ms 最少；
每秒累计被延迟 217~280ms。

**改法（不换模型、不改周期、不碰后处理）**：`core.dml_lock.TICK_BEAT` 记「感知放锁」节拍
（`yolo_detector` 放锁后 `note()`）；深度 worker 取帧前等一次新节拍、再等本拍的 push 落地
（拍内 push 在感知之后 ~6~10ms，只等节拍会取到上一拍的帧）；只在控制拍在跑时等（最近一拍
在 1s 内），否则不空等。前向从「感知刚放锁」起跑，伸进下一拍收到几何下限 ~19ms（54 − 拍内
空档 42 + 预处理 7）；等 push 后再起跑约 25ms。

**首轮跑局（2026-11-04_085659，3611 拍）**：
- 达标：`yolo_wait` p90 41.9→**25.4**、p99 53.6→**30.1**；40~54ms 那一档 96 次→**4 次**；
  `cum_delay` 217→**147ms/s**；拍间隔 p90 74.2→67.0、>60ms 占比 36%→28%；窗外等待均值 10.3→2.1。
- 越线并已修：`depth_age` p90 356→**395**（越过 350 闸）。根因是等完节拍取到的是**上一拍**的
  帧——`queue` 段 p50 20.7→47.5（正好一拍）；修法=节拍后再等「push 序号变化」（上限 30ms）。
- 解释项：`caught_per_forward` 2 拍档 8.3%→15.9%，与前向时长漂移同向（本局 forward p50 58.1ms，
  基线中 forward 60.3ms 的局 2 拍档也是 15%），不是错峰引起的——判据须按前向时长归一。

**修后复验（2026-11-04_102448 / 120417，队列段 47.5→1.1ms，取帧修复生效）**：
- 干扰：`yolo_wait` p90 27.4/35.3、p99 32.2/39.7；40~54ms 档 4/22 次（改前 86~120 次/局）；
  `cum_delay` 145/171ms/s；`wait_outside` 1.9/0.8ms。尾巴问题解决。
- 新鲜度代价：`depth_gap` p50 160/167ms（改前 117~134，等下一拍所需），`depth_age` p90
  353.8/369.6（改前 302~356，贴 350 闸上沿）、复用拍占比 49~51%→59~61%。
  其中 102448 局 forward p50 64.8ms（比基线慢 ~20%），该局等待与年龄整体更高，非排期差异。
- 结论：干扰目标达成；年龄停在预算上沿。要继续收回需让后处理与下一轮前向并行（架构改动，
  当时无错峰时才回退过；错峰已把识别空档显式造出，两者叠加需单独验证）。

**验收（下一局用 `probe_schedule_cap.py` 同口径对照）**：
- 主：`yolo_wait` p99/max 从 ~54/~96 落到 ≤25；`caught_per_forward` 的 2 拍档不得上升
  （按 forward 时长归一，见上）；`cum_delay` 从 217~280ms/s 降。
- 副：`busy_skips` 掉到 0 附近（不再抢输白干）；`depth_gap` p90（220~266ms）收敛。
- 反向闸：`depth_age` p90 不得越过 350ms 闸、断供率不得上升——错峰把周期拉长会推迟
  「下一张」，晚消费的年龄会随周期上浮。再触闸就缩短节拍等待（最近一拍 ≤30ms 才等）或回退。
- 得分率不作为本门判据（用户 2026-11-03 明确：得分关系不归本轮；G4 已证既有分布内无关联）。

**回退面**：`core/dml_lock.py` 的 `TICK_BEAT`、`core/yolo_detector.py` 的 `note()`、
`depth_geo` 的 `_stagger_wait` 与三个常量（STAGGER_FRESH_S / STAGGER_WAIT_S / PUSH_WAIT_S）
——删掉即回到自由起跑。

## 写死的停止条件

1. 生命周期与锁行为已能解释主要延迟，**不为更精确的数字无限加埋点**。
2. G3 子图实验若不能在可接受总耗时内保留融合收益 → **放弃时间切片路线**。
3. G4 若得分对 YOLO 等待与深度 age 均不敏感 → **停止本轮优化**，回到游戏成绩本身。
4. 仅通过上述门槛才进生产代码改造。
5. 改造后必须用**真实驾驶 score rate** 验收，不以 GPU 利用率 / 单次推理耗时 / 平均延迟替代。

## 附带必须记录（随 G3）

- **缓冲所有权**：raw 输出（IO binding 固定缓冲）会不会被下一次 Run 覆盖；拷贝/双缓冲实际成本。
- **分段续跑语义**：worker 是 latest-only 非阻塞抢锁（[depth_geo.py:413-414](../../../maaracing_master/plugins/speedrush/depth_geo.py#L413-L414)），
  劈成 K 段=要复抢 K 次锁，任一次 Busy 即**整帧作废**——切片要求新增"序列预留/准入"机制，
  这是架构改动，必须单独审查，不得藏在性能优化里。
