# maa-teardown-crash — 跑图框架收尾析构是否安全

## 要回答的事实

C 类（外部系统行为）：MaaFramework 的 Python 绑定在**任务已停止后**，
把 Tasker / CustomController 交给 Python 垃圾回收（`gc.collect()`）销毁，
是否可能触发 `0xC0000005`（访问冲突，出错模块 MaaFramework.dll）？

以及：若改为**显式、有序地先销毁框架对象**（在任务确认结束后、其它清理动作之前），
是否消除该崩溃？

## 现实背景（触发本次实验的现象）

GUI 点停止后界面永远停在「停止中...」，但游戏动作确实停了。
系统事件日志在停止后 1 秒记录 `python3.11.exe` 崩溃：
`MaaFramework.dll` / `0xC0000005`，近七天 6 次，偏移集中在两个相邻地址。
运行日志停在收尾阶段的「虚拟手柄已销毁」一行——紧随其后正是 `gc.collect()`。

## 判据（标尺独立于待验证对象）

- 判据 = **子进程退出码**：`0` 正常结束；`0xC0000005`（十进制 -1073741819）即复现崩溃。
- 不依赖被测代码自报状态，不采信「看起来正常」。
- 两组对照：`gc`（现状：对象留给回收）vs `explicit`（修复设想：先有序销毁再回收）。

## 运行

```bash
.venv/Scripts/python.exe tools/experiments/maa-teardown-crash/probe.py --mode gc --iters 20
.venv/Scripts/python.exe tools/experiments/maa-teardown-crash/probe.py --mode explicit --iters 20
```

父进程逐次拉起子进程（单次崩溃不污染整轮统计），逐次打印退出码并汇总。

## 结论（2026-10-26）

| 组 | 停止方式 | 销毁方式 | 崩溃 |
|---|---|---|---|
| `race` | 不停，任务仍在跑 | 交给回收器 | **10/10** |
| `gc` | `post_stop` + 等任务 | 交给回收器 | 0/20 |
| `gc --settle-ms 0/50/200` | 同上 | 同上 | 0/10 各 |
| `stop-only` | 只等停止请求 | 交给回收器 | 0/10 |
| `explicit` | `post_stop` + 等任务 | 有序显式销毁 | 0/30 |

**成立**：

1. 框架 worker 仍在活动时销毁 C 句柄 → 必然 `0xC0000005`，出错模块 MaaFramework.dll
   （与真机崩溃同模块、同异常码）。
2. 停止请求完成后任务句柄同步结束；此后销毁稳定，与收摊宽限无关
   （0 / 50 / 200ms 无差异）——**关键是「等停止完成」，不是「多睡一会」**。
3. 销毁顺序（交给回收器 vs 有序显式）在「已停止」前提下都安全，差别在时机可控性。

**未复现**：真机偶发（约 10%）的具体触发条件。真机链路比本模型多出双跑图器、
虚拟手柄、WGC 原生采集、模块线程与自定义回调图，回收顺序与时刻都更不可控。
故修复按「消除机制」落地：销毁时机与顺序由代码显式控制，不再交给收尾阶段的全堆回收。

**修复落地**：`nav_graph.py` 的 `NavGraph` / `NavKitV4` 停止时同时等停止请求与任务句柄，
`shutdown()` 在销毁前先停、再按序置空句柄；`treasure` 模块 cleanup 补上跑图器释放；
前端连续轮询失败到阈值即明说「后台已断开」并禁用按钮。

## 第二轮：停止请求被重复投递（同日修复后暴露）

修复上线后真机日志出现新告警：点停止后 10 秒才出现「停止请求超时未完成」，
且位置在收尾完成之后。逐条排除候选机制：

| 候选机制 | 实验 | 结果 |
|---|---|---|
| 任务停止后再发停止请求 | 间隔 0 / 0.5 / 2 / 5 / 10 秒 | 均 0.01~0.03s 完成 |
| 两线程并发同时发停止请求 | barrier 同步两线程 | 均 0.02~0.03s 完成 |

最小模型复现不出「句柄不推进」。定位依据来自真机日志的**位置**：收尾各步
（停止截图、恢复音量、手动停止判定）都在同一秒完成，10 秒超时出现在收尾之后
——说明卡住的等待**不在收尾线程**，而在点停止的请求线程（模块停止路径 →
跑图器停止 → 等收摊）。

结论：停止请求会被两处并发触发（GUI 请求线程 + 跑图线程中断路径），
真机复杂图下其中一次的句柄不推进，白等满一个超时。修复两条：

1. 每轮只投递一次停止请求（锁内去重）；任务已结束时不再投递（没有可停的东西）。
2. 模块停止路径只投递、不等待——等待交给跑图线程的中断路径，避免占住请求线程。

**未验证**：最小模型未复现「重复投递导致句柄不推进」，此结论依据真机日志的时序
位置推出。若修复后仍有超时，日志里的「来源」字段会指明是哪条路径。
