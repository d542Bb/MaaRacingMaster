# speedrush 驾驶感知实测（2026-09-16）

回答的问题：**旧 racing 的感知件能否直接搬到 speedrush 驾驶上？** 属 C 类问题（外部系统
行为——跨画面域的模型/算法表现），按守则必须实测，禁止靠猜。

## 素材与方法

- 帧源：维护者提供的 speedrush 真机窗口截图（15 张进入流程 + 2 张驾驶），
  1281×759 窗口截图，裁出 720p 客户区（`x=1 / y=38` 偏移，见 `docs/CODE_WIKI.md` §9.7）。
- 驾驶帧定位：以驾驶页独有的档位图标 `speedrush_drive_gear.png` 做模板匹配，
  >0.85 判为驾驶页。**16 帧中仅 2 帧是驾驶页**（gear 分 1.0000 / 0.9788）。
- 模型：`archive/racing/resources/onnx/model.onnx`（racing 时代 3 类微调，coin/car/bonus_car）。
- 探针：`probe_legacy_model.py`。

## 结果

### 1. 检测器在 speedrush 帧上的表现

| 帧类别 | 帧数 | coin | car | bonus | raw(阈值 0.05) |
|---|---|---|---|---|---|
| 进入流程 UI 页 | 14 | 0 | 0\~2 | 0 | 0\~12 |
| **驾驶页** | **2** | **0** | **0\~1** | **0** | **4\~5** |

两张驾驶帧目视确认均为**空旷路段**：无金币、无障碍车，仅远处一辆对手车。因此
**"0 检出"与画面一致，不构成模型失灵的证据**——本批素材无法判定模型复用性。

反例：活动页帧（背景为赛车宣传画）模型能检出画报中的金币（0.62）与车（0.74），
说明模型对**画报式**的金币/车外观仍有响应。

### 2. 标线体系与 racing 不同（实测，比模型更要紧）

驾驶帧显示 speedrush 的道路标线是：

- **车道分隔 = 白色虚线**（自车左右各一条）
- **路缘/道路边界 = 黄色实线**（两侧，透视斜线）

而旧 racing 的 `_detect_lane` 是**「找黄色标线」**（HSV 黄色范围 `[20,80,80]`），把它
当作单侧"墙"喂给 `_wall_avoidance`。两者语义在本域发生了**漂移**：

- 黄色线在 speedrush 里确实存在，但那是**路缘**，不是车道分隔 → 旧算法的"墙"语义
  恰好仍成立（路缘就是墙），**这一半可复用**；
- 但旧算法**没有检测白色车道分隔线的能力**，它靠硬编码透视测量点
  （`_lane_boundaries_at_y` 的 `bound(0.22, 1.00)` 等分数）反推车道边界——
  本域白线**直接可见**，用硬编码反而丢掉了现成的观测。

### 3. 光照变化已证实

两张驾驶帧分别为**阴天**与**晴天蓝天**。用户此前描述的"两种天光"得到印证。
这对基于颜色的阈值型检测（旧 racing 的 HSV）是直接威胁，对学习型检测影响较小。

### 4. HUD 可读数据清单（供数据记录阶段）

驾驶页 HUD 含：`阶段:N`、倒计时、`里程`、`超车`、总分、`得分速度 X/s`、双方比分与
血量百分比、`极限超车` 横幅。均可用 rapidocr 在 Python 侧读取。

## 结论与下一步

- **模型复用性未证实**，需含金币/障碍车的驾驶帧才能判定。素材缺口如实记录，不下断言。
- 旧算法的**标线检测**部分确认与本域画面域不匹配（白线 vs 黄线），这是"旧算法差"的
  根因之一，且决定了新方案该怎么做。
- **车道结构已确认**：**4 条车道**，由 3 条白虚线分隔、双侧黄色实线路缘界边。自车左右
  各紧贴一条白虚线，第二条白虚线贴画面左缘且断续——初查因单帧漏认该线误读为 3 条，
  把路面左右两半各放大一倍逐一核对后纠正。观测时自车位于**从左数第 3 条**车道。
  标线形态与车道结构已录入 `RULES.md` §3.8。

## 街车检测充分性重测（2026-09-21，补上「素材缺口」那一半）

回答的问题：旧 racing 模型的 `car` 类在 speedrush 域**有街车时是否稳定认得出、跨场次/
天况是否一致**——决定阶段 B 感知是否需要重训。`speedrush_vision` 实验（2026-09-18）的
60 帧初判只回答了"能不能认"。

### 素材与方法

- 帧源：recorder 全量导出 **34 场 × 28329 帧**（1280×720 客户区帧，`demos/<场>/frames/`）。
- 探针：`probe_streetcar_coverage.py`（scan 逐帧推理 → jsonl；analyze 派生指标）。
  阈值口径与旧栈运行时一致（0.35、NMS iou 0.45、RGB 640 letterbox），走参数化后的
  `core.yolo_detector`（与阶段 B 同一条路）。

### 结果

| 指标 | 值 | 判读 |
|---|---|---|
| 有 car 检出帧占比 | 场均 73.6%（p10–p90 55–96%） | p1/p2 后缀实为**阶段**：阶段 1 街车稀、阶段 2 密（目视证实） |
| 框落旧栈语义带 y∈[201,561] | 92–99%/场 | 空间 sanity 过 |
| 自车嫌疑区（cx∈[600,680]∧y>600）误检 | **0.0%** | 自车从未被认成街车（追车相机钉中央，与 control-route 副产品一致） |
| 轨迹均值/最长（贪心最近邻） | 8–19 帧 / 34–191 帧 @15fps | 时序连续 |
| 近框（宽≥120px）conf 中位 | 白天 **0.89** / 黄昏雨 **0.88** | 近距跨天况一致 |
| 中框（50–120px）conf 中位 | 0.87 / 0.87 | 一致 |
| 远框（<50px）conf 中位 | 0.77 / **0.67** | 弱点：远距小目标，黄昏雨再降一档 |

目视甄别（5 帧，覆盖低检出场零检出帧与高检出场多框帧）：零检出帧为**空旷路面或消失点
附近 <15px 车影**——"画面里没目标"为主因，不是模型失灵（vision 实验教训的同款验证）。
9/21 晨场含**雨景**（镜头水滴、路面湿反光）与黄昏逆光，近中距检出均正常。

### 结论

- **阶段 B 感知不需要为"街车认不出"重训**：近/中距（决策点所在距离）跨天况稳定高置信，
  无误自检，时序连续。
- 已知弱点如实记录：**远距小目标（<50px）置信偏低且受天况影响**（0.77→0.67）。它影响
  前瞻距离而非决策点；是否够用，待 τ 转向延迟实测（阶段 B 开工前置）给出所需前瞻量后判定。
- 触发重训的条件（与"能不能认街车"无关，来自 vision 实验硬缺口清单）：需要拆分两类奖励车、
  需要金币组结构、或 τ 实测证明远距前瞻不足时。
- 疑点：083222_p1（雨）最长轨迹 191 帧（≈12.7s），远超一次超车的合理时长，疑为消失点
  附近滞留的远距误检被贪心关联串成；不阻断结论（近中距指标独立成立），留作阶段 B 联调时
  的跟踪器设计输入。

复跑：`.venv/Scripts/python.exe tools/experiments/speedrush_drive/probe_streetcar_coverage.py scan`
（约 6 分钟）后接 `... analyze`。逐帧结果在数据目录 `speedrush/streetcar_coverage.jsonl`。

## 维护者到场一轮打包计划（阶段 B 开工前置，约 30 分钟）

三件事共用一次到场、一套录制链路（recorder 全程开着，每场自动落盘）。按序执行：

### ① τ 转向延迟 + 惯性时间常数（十几分钟，`speedrush-drive-plan.md` §126 口径）

- 动作：直路中段保持 2s → 满舵左 1s → 回中 2s → 满舵右 1s → 回中 2s，左右各重复 3 次。
- 打舵执行二选一，**到场先定**：
  - **A. 程序下发**（推荐，时间戳精确）：经 vgamepad 通道打方波舵量，pads.jsonl 直接
    记录指令时刻；需先写一个一次性舵量脚本（半小时内的活，可开工前备好）。
  - **B. 手动打舵**：维护者物理手柄操作。**风险点先核**：recorder 轮询的是 XInput
    槽位（pad_slot=0），需确认手动输入与 vgamepad 虚拟槽位不冲突、pads.jsonl 能如实
    反映舵量，否则时间戳只能靠画面反推，τ 精度受损。
- 读数：pads 阶跃时刻 → 帧序列自车横向响应起始时刻 = τ；响应爬升形态 = 惯性时间常数。
  自车横向位移用追车相机特性（自车钉画面中央）改测**路面纹理/车道线的横向流动**。

### ② 全程直行基线（一场，验收判据 §二.2「基线须先测」）

- 动作：完整跑一场阶段赛，**全程零转向**（油门正常）。
- 读数：金币获得率（吃币计数/时长，直读通道口径见 `RULES.md` §7#4 浮字直读）——
  该值即阶段 B 闭环验收的基线，不得凭印象设目标。

### ③ 补采素材（顺带，每场约 40–90s 自动落盘）

- **§7#2 贴近阈值稳定性复测**：再录 3–5 场常规驾驶（干景即可，现有 9/19 素材同型），
  把 n=40/三场的样本量抬上去。
- **雨景**：已部分覆盖——9/21 晨场含雨景与黄昏逆光（本次重测目视确认），如需更多雨景
  场次再补。
- **高速场景**：现有素材未覆盖的高速段（若玩法可稳定进入）录 1–2 场，同时解 RULES
  若干 `[实测·待复核]`。

### 交付

录制目录（数据目录 `speedrush/demos/`）+ 本 README 追加「τ 实测」小节（τ、惯性时间常数、
直行基线三值）。τ 一出数，阶段 B 控制栈解除暂缓。

## τ 实测与直行基线（2026-09-21 到场轮交付）

到场按上文打包计划执行：局 1 左右变道（τ）、局 2 全程直行（基线）、局 3/4 正常玩
（阈值复测样本）。四局八场全部落盘（录制链路当日修复见「环境插曲」节）。

### τ（转向指令 → 画面横向响应延迟）

仪器 `probe_tau_steer.py`：pads 的 lx 阶跃（|lx|<3000→>20000，持舵≥0.25s）→
近场带（y∈[430,700]）phaseCorrelate 逐帧累积横向流，扣除指令前 ~0.5s 基线流速，
残差越 4px 即响应起点。实际执行为连续游戏打舵（非干净阶跃序列），但每次推舵的
上升沿仍是阶跃输入，可用。

- **τ 中位 0.130s**（n=51，p25–p75 = 0.087–0.147，min 0.004 / max 0.197）；
- **左右对称**：L 0.139s / R 0.127s（n=26/25），无方向偏差；
- 峰值横向流 25–50px、63% 上升 ~0.33s（响应起点后）；
- 精度受帧时钟 ~15fps 限制（±1 帧 ≈ 67ms），工程够用。

**对阶段 B 的意义**：Pure Pursuit 的 lookahead 下界 = τ + 控制周期余量，
τ≈0.13s 说明**画面响应延迟不是瓶颈**，lookahead 主要按速度与轨迹曲率定。

## 跟踪层离线回放（2026-09-21，§7.5 前置测量首版读数）

**仪器**：`probe_tracking_replay.py` 两段——`scan` 用运行时同一 `StreetPerception`
（插件自带模型、conf 0.35、全帧）把 42 场 35517 帧的三类框几何全量落盘
（`<data>/speedrush/tracking_scan.jsonl`，不入库）；`replay` 按会话喂 `Tracker`，
只消费公开输出字段统计。素材行率 ≈15.8Hz（47% 的 capture frame_id 缺号——主循环
~21Hz 对 30Hz 捕获的固有采样，**失联段长按素材行计**，1 行 ≈63ms）。

**读数**（3635 条轨迹、5886 个失联段）：

| 段长（行） | 段数 | 恢复占比 | 判读 |
|---|---|---|---|
| 1–2 | 1499 | ~99%（gone 仅 11） | **检测闪烁**——grace 要罩住的主力 |
| 3–6 | 1412 | 62% | 恢复/退场混合带（远处收敛与近处超车并见） |
| 7–9 | 2906 | ~1%（gone 99%） | **物理退场**：cy<450/450–600 近场车从屏下退出或被自车过顶遮挡 |
| 10+ | 69 | 0 | 尾部截断（宽限退役前未及恢复的极少数） |

- 恢复率对段长**单调衰减且在 6 行后归零**（7–9 行 gone 里 car near/coin/bonus 齐全，
  是目标真没了，不是关联门太紧——放宽门限救不回来）。
- far→near **晋升 1456 次**：金币组天然从远处来，`lane_side→x_lane` 的身份通道是刚需
  而非装饰（§一契约的 FarTarget 设计被数据支持）。
- 负载：近场目标 P50 ≤1、P95 ≤4；远场 P50 1、P95 ≤4——决策层每 tick 的候选集很小，
  评分预算宽裕。
- 轨迹寿命 P50=16 行 ≈1.0s、P95=87 行（长寿命=持续跟到近处的车）。

**结论与定档建议**：`grace_ticks` 起值 15 过宽——有效恢复窗右缘 ≈6 行（≈0.38s），
7 行以上几乎全是该退役的退场目标；建议 step 4 参数表定 **6–8**（决策保持段越长
越吃假阳性）。闪烁段 99% 在 1–2 行内恢复，对迟滞器意味着：失联 1–2 行的目标
在决策侧应视同在场（这正是 grace 的意义），不需要额外的"短暂消失"特判。
**[实测]** 口径：按素材行率 15.8Hz；实机 21Hz 主循环下行率略不同，grace 换算
以秒（≈0.4s）为准不按行。

## 金币组聚合口径回放（2026-09-21，§七.2 结题）

**仪器**：`probe_coin_groups.py`——输入 `tracking_scan.jsonl`（本节上一半的产物），
真 Tracker 给币发跨帧 id 后喂 `CoinGroupAggregator`，测四件事。

**读数**（42 场、coin 非空帧 771 邻对 / 组帧样本 5132）：

- **Δx_lane 双峰成立**：同帧相邻币 <0.3 占 58.6%（组内）、>0.6 占 30%（组间，
  P90≈4.9——"组间"主峰其实是 **≈5 车道的隔排远邻**）；0.3–0.5 过渡带仅 5%。
  **max_dx=0.3 站得住**，且它才是主分离门——cy 门只是防"同排不同组"的横切。
- **同组行距** P50=24 / P90=37 / max≈50px → 起值 40 切尾，**定档 60**。
- **跨帧组身份 Jaccard 干净双峰**：97.3% ≥0.8，[0.2,0.5) **零样本**——0.5 阈值落在
  谷底确认；组身份由跟踪 id 维系一环成立（币级 id 稳 → 组级继承稳）。
- **组内间距完全均匀**：三枚组样本 n=25，max/median_gap 恒 =1.0——金币排布是
  等距阵列（RULES §7#3 组结构的一个几何侧面）。**gap_factor=1.8 实测零触发**，
  partial 判据现行无价值但无害，保留等 step 4 真实漏检形态。
- **partial 13.1% 全部来自存续组**（670/5132，本帧 0 成员的宽限保持）——
  "组内缺币"意义上的 partial 一例未出。语义分账：存续组=观测缺口，
  与"等距阵列中间缺一枚"是两件事，step 4 评分器区别对待。
- **多枚组稀（有成员帧里 ≥2 币仅 288/5132=5.6%）不是聚类错误**：币行天然在远处
  （cy 集中 327–353，denom<20 大多在域外），进域是逐枚发生的——**证实 §一
  far→near 晋升通道是组聚合的生命线**（与 §7.5 晋升 1456 次互证），也意味着
  评分侧"组大小"要到近处才看全（early 预告只给枚数下限）。

**结题**：max_dx 0.3 确认 / max_cy 40→60 / jaccard 0.5 确认 / gap_factor 维持待样。

## 离线全链路回放（2026-09-21，§八 step 5；§七.1/§七.3 一并收口）

**仪器**：`probe_replay_chain.py`——到场轮 8 场 7188 帧，感知→Tracker→金币组聚合→
边界摘要→DecisionEngine 全链逐帧跑通，决策输出落 `<data>/speedrush/replay_chain.jsonl`。

**链路实情与修正（step 5 的存在意义，证据 commit `db7ccde`）**：
- **frame_id 相等重复是合法输入**：WGC 中心缓存 + 主循环 ~21Hz 读 30Hz 画面，必然
  两拍读同一帧（回放第 833 帧即抛 ValueError）。原契约"严格递增拒绝重复"实机接线
  第一天就会炸——修正为"同号=原样重发缓存观测（不重关联/不老化/不抹零速度估计），
  倒退=仍 fail-loud"。

## K_v 前提证伪：杆是航向指令不是平移速度指令（2026-09-22，V1 p2 真机 trace）

**结论**：不存在"杆值→稳态横向速度"的静态增益 K_v——赛车机制下杆命令**车头航向**，
横向位移是双积分（满杆按住起步段 x∝t²）。上一条目"K_v 测不出"的真实原因不是数据噪声，
是**物理上没有可拟合的稳态映射**；"目测满杆跨一道几秒"的悬置问题一并关闭。维护者提出，
p2 trace 判决确认。

**证据链（trace_20260922_145645_p2.jsonl，四段持续 ≥3 拍的深杆区间）**：
