## 1. 驾驶页锚点：齿轮图标的来历与它的漂移（本域实测）

通用采集纪律（半透明元素、裁剪、命名、坐标系换算）见主文档 §9.7；**本域的具体证据与数据
在此，主文档不复述**。

**第一版锚点是 HUD 上的"阶段"二字，实测不合格。** 它压在动态画布上半透明，像素逐帧与背景
混合——两种天光下跨帧匹配分 **0.94 → 0.71**，跌破阈值即失配。

**改用同区域的齿轮图标（不透明）**，当时读到跨帧 0.93，判为"稳定"。

**2026-09-16 两轮录制帧复核推翻了"稳定"这个结论**：

| 情形 | 锚点分数 |
|---|---|
| 驾驶途中（多数帧） | 0.93 ~ 0.99 |
| 驾驶途中（漂移段，**仍在驾驶**） | 缓降到 **0.80** 并成平台 |
| 真正离开驾驶页（画面切走） | **0.02** 量级（几乎归零） |

- 漂移的成因不是透明度，而是**彩色匹配（`colorspace: rgb`）把搜索区内的背景色一起算进
  相似度**——一例阴天灰底、一例晴天蓝底，齿轮本身没变形。改 `gray` 后 p50 由 0.919 升到
  0.970、漂移段 min 由 0.800 升到 0.843（有改善，但余量仍薄，不是根治）。
- **两端分离度极大**（0.02 对 0.80，约 40 倍），所以阈值取中间即可，两侧都能留足余量；
  节点当前取值见 `resources/pipeline/speedrush.json`。

**踩过的两个坑（都值得记）**：

1. **阈值不能用单天光、单轮样本标定。** 最初依据"跨帧 0.92~1.00，阈值 0.8 有余量"设了 0.8；
   实机出现 0.80 的驾驶帧后分数贴着线抖动，连续两次未命中被误判成"阶段结束"——流程随后去
   找奖励弹窗，而画面还在驾驶中，白等 20 秒后中止。**单轮样本的"稳定"是假象。**
2. **"半透明不行 → 换不透明图标"只解决了半个问题。** 背景会从"颜色"这一侧回到分数里；
   只换图标而不改匹配口径或标定方式，同一个病会再犯。

**兜底方向**（尚未实施）：多锚点 Or 组合（主文档 §9.7 已提），或直接读 HUD 上的 `阶段:N`
文字——那是**事实**而非推断，但它半透明，只能走 OCR，不能走模板匹配。

## 2. 驾驶阶段门控与循环节拍（本域）

- **驾驶页锚点节点的 `rate_limit` / `pre_delay` / `post_delay` / `timeout` 在图上显式置零或
  调小**：它是纯页面判定，不需要"每轮识别最低消耗"的地板，也不需要隐式等待；超时留短值让
  未命中时快速收尾。吃框架默认值的实测后果：主循环被压到约 1Hz（52 秒只录到 65 帧），
  且阶段结束要驻留 20 秒才记一次失配（容差要求两次 → 40 秒）。
- **流程步骤节点保留默认超时**：那些步骤本来就要等按钮出现，短超时会误判失败。
- 判据：就绪 = 连续命中若干次；离开对局 = 连续失配若干次（次数与间隔见 `module.py` 常量）。
- 循环退出时报一次实际节拍（轮数 / 秒数 / Hz）。**这是"采集能不能支撑训练"的第一手判据**，
  此前日志只有帧数没有速率，偏差看不出来。
- **2026-09-16 实机复测：两阶段各跑完整一段（未再出现途中误判）**，进入与离开的判定帧
  逐张翻图核对过——进入帧落在驾驶页（不是起步动画），离开帧分别落在奖励弹窗与回合结果页
  （不是过场动画中间）。阈值放宽到两端分离度的中间后，"贴着线抖动"这个病没有再犯。
  节拍与修复前的对照见日志的 `循环结束` 行（采集帧率受锚点复查的框架往返开销限制，
  不是采集侧也不是写盘侧；该开销尚未优化，方案里 30Hz 是控制期的目标）。

### 2.1 节拍已量化：**录制帧率不是独立旋钮 = 主循环迭代率**（2026-09-18，九场 5586 个帧间隔）

| 量 | 实测（九场一致） |
|---|---|
| 有效帧率 | **15.1~15.3 fps** |
| 帧间隔中位 | 49.9 ms（名义 50 ms） |
| 帧间隔 **P95** | **200 ms** |
| 分布 | 0~40 ms **36.4%** · 40~60 **33.7%** · 60~100 **17.1%** · **100~300 ms 12.6%** · >300 0.2%（最长 688 ms） |
| 慢间隔的**周期** | **每 8 帧一次**（704 个相邻慢间隔里 **688 个恰好隔 8 帧**） |
| 单次锚点复查净开销 | 约 **130~250 ms**（慢间隔 183~300 ms 减去约 50 ms 的常规迭代） |

**机制**：`record_frame` 在主循环里**每迭代调一次**，所以"录制帧率"**不是独立旋钮，它就是
主循环的迭代率**；而主循环里 `DRIVE_ANCHOR_CHECK_S = 0.5` 的锚点复查（一次 `graph.run`
识别往返）是唯一重活 → **7 帧常规 + 1 帧拖尾 = 8 帧 / 0.52 s = 15.3 fps**。
**周期对得上就是根因**：8 帧 × (1/15.3 fps) = 0.52 s ≈ 0.5 s 的复查周期。

**同时排除了另两个嫌疑人**（都量过，无责）：

- **源比我们快得多**：`frame_id` 是 WGC 回调**接受**的帧号，其推进速率在正常与慢间隔期间
  **都是约 40 帧/秒**（正常间隔 dt≈50 ms、id 增 2；慢间隔 dt≈200 ms、id 增 **7~8**）。
  采集上限 `max_fps=60` 没吃满。→ **每 0.5 s 有一批约 40 fps 的帧被接受，却只有 1 帧被记录**，
  中间帧被"最新帧槽"覆盖（进不了队列）——**约 60% 的帧在采集侧就被白扔了**。
- **写盘与队列无责**：九场 `frames_dropped` **全为 0**；`age_ms` 中位 13.3 ms、**最大 33.2 ms**，
  且慢间隔处的 age 与快间隔一样小（13~14 ms）——帧到回调时都新鲜，没有任何积压。
- 手柄线程也没问题：`pad_poll_hz=200`，实测 193 Hz。

**目标帧数怎么定（三个消费者，不是一个数）**：

| 消费者 | KPI | 结论 |
|---|---|---|
| 运行期（实机推理） | 控制周期 + **尾延迟** | 20 Hz ⇒ 50 ms 周期、2~3 s 视野 = 40~60 步，够用；但**τ 未标定前提高帧率不提升控制精度** |
| 离线观测（浮字这类 0.13~0.4 s 的事件） | 一个事件里 **≥2~3 帧** | 15 fps 下 0.13 s 只有 2 帧，且 P95=200 ms 的尾延迟一次就能吞掉整个事件 → 要余量得 20~30 Hz，**判据用 P95 间隔 ≤100 ms，不用平均 fps** |
| 训练 / 标注 | 与帧率**正交** | 相邻帧近乎重复；按帧率扩数据只让标注线性膨胀，应按**多样性**采样 |

**故建议的口径（待维护者定）：名义 20 Hz、且 95% 的间隔 ≤100 ms**——不用 30 fps：
源的上限（约 40 Hz）不缺余量，20 Hz 对控制与观测两边都够，而存储实测 **154 KB/帧**（九场中位）
——15 / 20 / 30 fps 分别是 **138 / 184 / 277 MB/分钟**，一个 6 分钟回合按 30 fps 就是 1.5 GB。

### 2.2 已修：锚点复查的 200ms 是 `NavGraph.run` 里的**固定轮询间隔**，不是识别慢（2026-09-18）

按 §2.1 的判据继续下钻，**那一整段停顿与识别无关**——`NavGraph.run` 的完成轮询写的是
`while not job.status.done: … time.sleep(0.2)`：**单节点图哪怕毫秒级跑完，也要空等满 200 ms**。
（`load()` 有 `_loaded` 幂等，管线不是每次重投；截图走 `WgcapController.screencap` 读中心缓存帧，
也不自截——两个"看起来像原因"的都排除了。）实测停顿 183~300 ms ≈ 200 ms 轮询 + 识别 + 抖动。

**改动**：轮询改为**自适应短间隔**（`RUN_POLL_MIN_S = 1ms`，×2 退避到 `RUN_POLL_MAX_S = 20ms`），
中断检查每轮照做、语义不变；长图靠退避上限兜住 CPU（50 次/秒）。**这是 core 级改动，
所有插件共用**（`NavGraph.run` 是通用阻塞跑图入口）。
**回归锁**：`tests/test_navkit_v4_runner.py` 三个用例——20 ms 完成的图必须 <100 ms 返回
（用旧固定间隔必红，已做活性验证）、需多轮轮询的图仍正确等到返回真、中断路径发 `post_stop` 且不空等。

**实机复核（`20260918_191511_p1`，修复后一段 40.2 s）——尖峰消失，但**未到 30 Hz**：**

| 量 | 修复前（九场） | 修复后 |
|---|---|---|
| 有效帧率 | 15.1~15.3 fps | **21.0 fps**（日志独立报 `836 轮 / 40.2s（实际 20.8Hz）`） |
| 帧间隔 **P95** | 200 ms | **66.8 ms** |
| 100~300 ms 档 | 12.6% | **0%** |
| 慢间隔次数 | 75~98 | **7**（其中 3 次在起跑 1.0~1.3 s，属启动；另 2 次 388/433 ms 在 t≈28 / 39 s） |
| `frames_dropped` | 0 | **0**（帧率涨了、写盘量涨了，队列仍未满） |
| 源速率 / 每记录 1 帧之间源接受 | 38 帧/秒 / 2.43 帧 | 38 帧/秒 / **1.8 帧** |

→ **"每 0.5 s 被插 200 ms"这个病治好了**（成 12.6% 的硬网格化成 0），已按约定口径
（名义 20 Hz + P95 ≤100 ms）**达标**；**故不启用"把取帧入录解耦到独立定时线程"那一支**。

**但 `DRIVE_TICK_HZ = 30` 没到**，且**原因不再是尖峰**：帧间隔里已无 100~300 ms 档，说明
**循环是均匀地按 48 ms/迭代在走**（40.2 s / 836 轮），而不是"33 ms + 偶发长停顿"。
即每迭代有约 **15 ms 的去向未归属**（或迭代自身工作量 ≈48 ms）。本轮已**排除**的候选：
计时器粒度（手柄线程设定 200 Hz、实测中位 5.24 / P99 5.91 ms，粒度没问题）；其它线程把 GIL 饿死
（同上，手柄线程节拍很紧）；写盘积压（`frames_dropped` = 0）；周期性尖峰（已消失）。
**尚未归属**。要定它只需给循环加一行**分相位计时**（取帧 / 入队 / 锚点复查 / 睡眠前后），
跑一段即可——**这属于"要不要追 30 Hz"的独立议题，不是当前口径的欠账**。

**另有一条不变式**：录制帧率一旦定下，就要与运行时推理**用同一个数**（K 帧堆叠的时间跨度
必须一致，见 `recorder.py` 文档头），不能一处 20 一处 30；`recorder.py` 头注释现在写的是
30 fps，改口径时同步改它。

## 3. 演示数据录制（本域）

- 一个会话一个目录：`data/speedrush/demos/<时间戳>_p<阶段号>/`，含 `meta.json`、
  `frames.jsonl`、`pads.jsonl`、`frames/`；一局两个驾驶阶段各成一会话，便于按阶段筛。
  录制模式下还会多出 **`hud.jsonl` + `hud_meta.json`**（驾驶页 HUD 读数，见 §5）。
- **录制模式放宽两条启动约束**：不要求断开物理手柄（录制正要用物理手柄驾驶）、不需要手柄
  能力（录制期不创建虚拟设备，机器没装 ViGEmBus 也能录）。机制见主文档关于
  `ActivityModule` 启动约束的说明。
- 门控判定日志带 `frame=`，与 `frames.jsonl` 的 `frame_id` 对齐（日志墙钟只到秒，帧号才是
  可靠的共同坐标）。导出判定时刻的画面用
  `tools/experiments/speedrush_gating/export_gating_marks.py`。
- 帧文件名是**序号**（`000001.jpg` 起，`seq` 从 1 递增），不是帧号；`frame_id` 只在
  `frames.jsonl` 里，两者的桥是那份索引的 `file` 字段。

## 4. 节点的 ROI：按「单帧模板外扩」定，会在同一按钮的另一页失配（本域实测）

**症状**：实机跑到最后一页（段位分结算页）卡死——`点继续` 识别未命中，驻留重试
20 秒后本轮中止。

**根因**：`点继续` 一个节点服务两个页面（回合结果页／段位分结算页），两页的按钮位置
相差约 **18px**；而它的 ROI 是 `locate_templates.py` 按「模板每边外扩 15% 宽 / 25% 高」
**从单帧**算出来的，只剩 8px 余量——结算页整个落在搜索窗外。

用仓库自己的匹配内核在结算页截帧上复算（同一素材、同一尺度集）：

| 搜索范围 | 得分 | 说明 |
|---|---|---|
| 节点 ROI 内 | **0.568** | 低于阈值即失配——搜索窗把按钮切掉了 |
| 全图 | **0.888**（按钮真实位置） | 按钮就在画面里，只是比标定位置左了 18px |

**判据**：模板没坏、阈值没坏，坏的是**搜索窗**。`rect` 是「这个按钮**可能**出现在
哪里」，不是「它上次出现在哪」；一个节点服务多页时，ROI 必须覆盖各页位置的**并集**
再留余量。修法是把该节点的 rect 放宽到并集（当前取值见 `templates_roi.json`），
**不是**加模板、更不是降阈值——0.568 那个量级会放行大量误命中。

**顺带查出的第二件事：真源曾经不能由生成器复算。** `build_truth.py` 把节点一律写成
模块默认阈值，且不输出驾驶页锚点的 `rate_limit / pre_delay / post_delay / timeout`
——即 §1、§2 两处实测修复当时只活在「生成之后的手工编辑」里，跑一次生成器就会把它们
静默抹回默认值（阈值回到默认 → 漂移段误判复发；默认节拍 → 主循环回到约 1Hz，而这两处
都已由实机复测确认修好）。现改为由 `NODE_OVERRIDES` 表声明例外，并加回归锁
`tests/test_speedrush_truth.py`：断言「生成器输出 == 入库真源」。

**教训（与 §1 是同一条）**：单帧标定出来的「够用」是假象。阈值如此，ROI 也如此。

## 5. 驾驶页 HUD 实时读数（本域）

**是什么**：`hud.py` 的 `HudObserver` —— 驾驶途中在**独立低频线程**里取帧、按区域真源逐格
识别，把读数落成会话内的 `hud.jsonl`（每行一次采样）。**读取范围不含左侧卡片三格**（里程 /
超车 / 合计）——它自 SCHEMA 5 起停读，理由见本节「卡片三格为什么停读」（口径与显示语义的
正本在 `RULES.md` §4.8）。

**为什么这样切**（改动前先读这三条）：

- **不碰 30Hz 驾驶循环**：单 ROI OCR 是 10~30ms 级，同步调用会把主循环拖慢一个量级。
  观察线程自带节拍（间隔见 `hud.SAMPLE_INTERVAL_S`），只做一次**非阻塞**取帧
  （`capture.frame_with_age()` 是 WGC 中心缓存的共享引用，多消费者各按自己节奏读是它的
  既有契约）；**首个样本推迟一个间隔**，阶段短于一个间隔时全程不碰 OCR。
- **行为与既有门控一致**：不创建虚拟手柄、不改驾驶循环节点的显式参数；观察线程与录制器
  **同一时机**启停（就绪后启、阶段结束的 finally 停），且**必须挂在录制会话上**——对齐
  目标就是同会话的 `frames.jsonl`，非录制模式既无会话目录也无帧索引可对。
- **通道序只走 `core.image_io`**：识别入口一律 RGB（`core.ocr` 对外收 RGB），本模块不写
  `[:, :, ::-1]`、不用 cv2 读图。

**读数结论的标尺与纪律（本域返工之后立的判据，改动读数相关代码前先读）**：本域的返工不在
"读数不准"上，而在**读数对、解释错**上——左侧三格逐格都读对了（与画面数字逐一相符），却据
"看起来单调递增"把它判成"本阶段累计里程"（后由连续读数推翻为约 10 秒的窗口小结）；同类还有
"矮版变体"（实为同一张卡片淡入中）与右侧四格的身份。解释错之所以穿透得远，是因为假设同时被
写进了**名字、真源与文档**三处，推翻时要一起改。三条常驻判据：

1. **独立标尺是人眼看帧**：同一条读数链路内部的"多字段互证"**不算**独立验证（它只证明仪器
   自洽）。语义结论必须配 `review_run sheet`／探针 `overlay` 出的图目视核对，且核对的是
   **画面语义**——哪一格是谁的、那一格是空区还是数字。
2. **语义结论要回答跨帧性质**：该不该单调、该不该重置、该不该上下互换、取值该不该落在某个
   范围里。单帧读对不构成语义证据；离线结论一律过 `review_run check`（拼写 / 自洽 / 单调不降
   等序列判据都写在那里），在线只有单格 `trusted` 与归属 `side` 可用——别在模块里另加"语义推断"。
3. **名字与真源不得承载未验证的语义假设**：区域键只用中性名（槽位 `a`/`b`、序号），身份由
   数据里的 `side` 承担；未验证的假设只写在 `RULES.md` 的 `·待复核` 条目与实验记录里，
   **升格为契约（键名、真源字段、生产分支）之前必须先过前两条**。
   **已验证的事实是例外**（2026-09-18 起）：读数框的键名带**卡片色**（`score_blue_a` …），
   依据是"两卡版式实测不同" + "蓝＝本机"三重佐证（官方规则页、维护者口径、「得分速度」行
   只在本机卡上出现）。判据管的是**未验证的**假设；把已验证的事实也赶出名字，只会让人在
   代码里偷偷按它分支。例外必须同时满足两条：**有实测/权威出处**，且**机检锁住形态**
   （测试要求真源两色两槽齐备、且只有本机卡有速度行——少一色就说明有人在按固定朝向写框）。

**已解问题（历史）**：里程口径（段累计 vs 滚动窗口）当年由这张卡片的连续序列定案为**约 10 秒
的窗口小结**（见 `RULES.md` §4.8）。为它立的 `settled`（定值）判据——卡片三行数字滚动爬升到
定值，爬升段的值看着合理却只是动画中间帧——随卡片停读一并移除（SCHEMA 2~4 期间每格带该位，
`hud_meta.json` 曾声明 `settled_fields` 与 `settle_gap_s`；旧会话的 `hud.jsonl` 仍按旧格式读）。

**卡片三格为什么停读（SCHEMA 5 起）**：维护者确认（`RULES.md` §4.8）——那张卡片每周期只在
后段约三秒显示数字，随后进度条进入"经过了一段时间"的状态，**其间三格不显示而统计仍在后台
累加**；故可见值是**滞后一个周期**的固化快照，作为实时判据不可用。为它而设的在场闸门
（`field_on_dark`）、定值（`settled`）、`合计 < 里程` 与单字可疑两类假读标记**全部随之下线**
（它们只服务这三格）。**真源里仍保留这三格的 rect**：离线探针（自包含）要读它们复核游戏规则，
生产侧靠 `SKIPPED_FIELDS` 跳过——跳过是名单，读取范围仍是"真源键集减名单"，不写死其余键集。

**记录必须可审计**（行里同时有原始与判定，而不是只有解析值）：每格记**原始文本**、**解析值**、
**比分块按颜色判出的敌我归属**（`side` / `side_source`），以及逐格 `trusted` 与 `note`（理由
清单）。"没读到"与"读到 0"必须分得开：前者只带理由，后者带值与文本。`regions` 是区域集指纹，
用于事后确认"这行是拿哪套框读的"；`hud_meta.json` 另声明 `fields`（实际读的格）与
`skipped_fields`（声明不读的格）。

**读不到的格怎么办**：只带理由、不带值（`note` 写 `no_text` / `unparsable` / `ocr_unavailable` /
`read_error`），行照旧落盘——"读错"与"没读到"都不许静默，也都不许冒充读数。先前那两类
（`合计 < 里程`、单字面板读数）是**卡片专用**的形态，随停读一并下线。

**区域真源**：`resources/policy/hud_regions.json`（纯数据、无注释）。它自本模块落地起
**只此一份**：离线探针 `tools/experiments/speedrush_scoring/probe_hud_ocr.py` 的 `--rects`
缺省读它——两份 rect 会各自漂移。`load_hud_regions()` 按 `check_truth.rect_checks()` 的同一
口径校验（4 元数值、[0,1]、`x1<x2`、`y1<y2`），并额外要求**角色的键齐备**（判色带 `pair_*`、
读数框 `score_{色}_{槽}` / `rate_blue_{槽}`）、且**没有多余的比分/速度键**——半改名的真源
最阴险：旧键会被当成普通格照读、新框却没人用，结果是"能跑、值不对"，故一律 fail loud。
非法即降级不启（记 WARNING，`_state.hud_recording` 为假，可查）。键的**四种角色**由
`region_roles()` 给出（读格 / 判色带 / 读数框 / 跳过），机检锁住"每个键都有角色"。

**读数框按「卡片色 × 槽位」取名**（`score_blue_a` …，2026-09-18 起）：两块卡的**版式不同**
——本机那张多一行「得分速度」、比分**字号更大且右缘更靠左**（实测 ≈x1135，对手 ≈x1155），
两卡的图标位置也不同。故**同一个槽位里两块卡的数值带并不重合**：按槽位取一个"够大的框"，
会把对手比分的末位读掉（实测 8500→850）或把图标读进来。**判色带（`pair_*`）与读数框分家**
正是为此：判身份只吃像素、不做 OCR，否则"选哪块框"就得先知道身份，成了循环依赖。
方式的边界由**逐帧测量**定（测量表见实验记录）：场边那一侧另有一处坑——比分右缘紧跟一个
人形图标，框右界必须卡在"数字末位"与"图标左缘"之间。

**敌我判据的出处**：`pair_sides()` 的口径搬自上面那个探针（逐格复核立起来的），本模块是它的
运行期住户。**槽位不等于敌我**——两块比分面板会上下
互换，故行内四格 `score_a`/`score_b`（a=上档、b=下档）与 `rate_a`/`rate_b` 都只是**槽位名**，
敌我按块色成对判、单列在每格的 `side` 里；消费方按 `side` 取，不按槽位取；每格另记 `rect`
（这一拍到底用了哪块框）。**身份判不出时连比分格都不读**（标 `side_unknown`）：读数框要靠
身份选，猜一个身份去读等于把另一家的数字写成本方比分。

**得分速度只为本方显示**（2026-09-17 实机三场确认）：本机侧 100% 有读数、对手侧只有零星
几处（那是背景假读）。故速度格只识别"本槽是蓝"的那一格，另一格**连 OCR 都不做**、
标 `not_displayed`；归属判不出时同样不读（标 `side_unknown`）——不知道这一槽是谁的，
就没有理由把那里的像素当读数。

**归属必须成对判**（`pair_sides`，2026-09-17 起）：两块面板必是一蓝（本机）一红（对手），
而面板是**半透明**的——背景景物会给两块染上同一偏色，**单块绝对阈值**在白天蓝天场会把两块
都判成"本机"（实测一场 62/69 行错，下游据此产出 51 处假"比分回落"：两家的值被混进同一条
序列）。故归属按**两块之差**定（公共偏色抵消），差小于 `SIDE_PAIR_MIN_DELTA` 两块都弃权；
条带采样同时收窄到**最饱和的一撮**（色条本身），让色条而非背景主导。单块绝对判据在生产侧
**没有实现**（它的失效正是成对判的由来）；成对判不可用时（区域集缺一块、判据抛错）归属
**弃权**为 `?`，不拿单块阈值凑一个身份。
逐格记 `side_source`（`pair`/`abstain`）留痕——归属判错是这里最难事后归因的一类故障。

**坑点**：

- `seq` **按采样尝试递增**，缺口 = 缺帧或队列满丢样本（与 `frames.jsonl` 的 `seq` 同语义：
  缺口即证据）；计数进 `hud_meta.json` 与 `_state`。
- 反压照录制器：`put_nowait` 入队、队满丢样本计数，**绝不阻塞采样侧**。
- 引擎懒加载（`core.ocr` 唯一真源），失败降级返回 None、不抛；`hud_meta.json` 与录制器的
  `meta.json` 分文件，避免两个线程写同一文件。
- `timer` 是 `mm:ss` 倒计时，它的 `value` 按**秒**记（`parse_value`）；通用取整会把 `04:46`
  读成 4，看上去像"剩 4 秒"——读数对而解释错正是本记录要防的一类。其余格子取第一个整数。

## 6. 横向归一尺子的使用口径（标定 A1，2026-09-21 定档）（本域）

**它是什么**：把画面上的像素横向偏移换算成「几分之几个车道」的透视归一量——
消失点/地平线为基准（`u = vpx + a·(v − y_h)` 一族，公式与常数的真源在仪器代码，不在此复述）。
它防的是 trick 实验栽过的坑：**透视收敛让真实等宽的东西在像素上不等宽**，
未归一的像素横向差直接当距离用会产出方向性错误的结论（撤回先例见 control-route 状态块）。

**怎么复用（机械化流程）**：四步——建 y_h 冻结基准 → 对象认证（逐轨身份图强制）→
线位逐轨拟合 a(t)（窗口判据 = HUD stage，禁 VP 质量口径）→ 车道单位换算（冻结 `A_x_used`）。
逐步命令与仪器 = 标定实验 README「A1 定档轮」（实验已于同日收杆归档，溯源
[`db7a3fe`](https://github.com/d542Bb/MaaRacingMaster/commit/db7a3fe78973d9d155d350feac581d7530f5138a)，
需复跑时从该 commit 检出其实验目录物化（目录名见该 commit 的文件清单）。

**适用域（详表在「A1 定档轮」，此处只列纪律）**：

- ✅ 直道 × 低速/起步段：唯一有判决性干净轨的素材形态。
- ⚠️ 直道 × 巡航（干景）：Gate 1/2 几何口径可用、线位 a(t) 不可得——**两类结论不得互借**。
- ❌ 弯道帧（直线模型失效）、最左白虚线（贴缘断续，从未进判决轨）。
- ❌ 黄实线路缘**不作横向基准**（湿景阈值失效史）；其运行期边界用途另论。
- ❓ 湿景 × 全油门高速：**定档不宣称覆盖**。
- 任一验收不满足 → 输出「无观测」并走不变量 7 保守态，禁止带病数值下发。

**配套纵向口径（同日裁定）**：车速锚 = 得分速度底值（使用前提与禁令见 RULES §4.8
「得分速度」条；「0.83 对账轮」全文溯源 [`db7a3fe`](https://github.com/d542Bb/MaaRacingMaster/commit/db7a3fe78973d9d155d350feac581d7530f5138a)）；
左卡片周期里程**禁止**除以卡周期当车速。

**锁**：control-route「标定全绿前不得把像素横向差当距离用」的「全绿」= 本节定档，
2026-09-21 起解锁。

**关键设计事实**：
- **车道量对整帧均匀缩放不变**（u=fx·sX/sZ+cx 约掉 s）——DA 视差逐帧尺度漂移
  （CV≈14%）对输出无害；fx 绝对值误差进一步被逐帧 W_REF 标定吸收，内参常量
  只承担 fx/fy 各向异性（1.006）与主点。
- **内沿像素 u 一律经拟合平面反投影**（u = X·FX/Z_edge + CX）：墙基滑带像素的
  X 恒等于墙平面 X 而 u 任意，逐像素关联产出噪声 u；夹紧缘（真路障）才用其像素 u。
- **遮挡旗只由 YOLO 物体掩码触发**，ego 静态掩码只负责挖除——ego 车身在远行的
  横向 |X| 本就 >GAP，拿它判遮挡会把所有远行误杀（金标可用率 35→54/55 的教训）。
- **行带判据=行内地面像素的 Z 中位**（全行均值被墙面像素拉进近带，远景污染读数带）。
- **缘出画的行弃权**（触画框判据）；弯道行斜穿路面使远行宽度虚胀——只进读数
  （逐行一票），不进尺度标定（标定带 Z<9、取 25 分位）。

配对宽度守卫兜底。结构边界（护栏/墙基）与黄线车道缘在本路型上不重合，road_offset
语义=「两侧最近结构的中点」，与 hsv 时代（黄线缘）不同——planner 手感差异属预期。

**自车伪缘修复与守卫重标（2026-09-27，trace 181518 局金标量测 17 帧）**：
①**动态自车吸收**（`_grow_ego_above`）：静态矩形掩码盖不全车形（尾翼出矩形），
泄出像素被 GAP 夹紧判据读成缘——实拍右缘=自车侧面 +0.35 道、6/18 帧有一侧
|lane|<0.5 嫌疑读数。修法=与静态掩码连通的近场上凸体（Z<EGO_ABSORB_Z=10，
防远场路墙投影落进矩形把整段墙链进吸收）整域并入挖除区后重拟合；再留保险丝：
夹紧段贴挖除洞 ±CLAMP_TOUCH_PX 置该侧遮挡弃权。重放实证 6 帧嫌疑读数全消
（d00004 右缘 +0.34→+2.03 真栏基），off 分布 ±0.45→±0.18。②消费守卫按结构
语义重标：HW_MIN/HW_MAX/OFF_MAX = 1.5/3.2/3.5（hsv 黄线口径）→ **0.8/2.2/2.5**
（金标量测：本路型结构配对半宽 p10≈0.9）；新增 hw EMA 一致性门 HW_LEARN_TOL=0.6
（对宽偏离记忆超此值不学，防幸存者偏差投毒——本局 EMA 被假宽对喂到 2.03）。
金标对比：逐行一致性 MAD 0.16/0.26→0.12/0.12，残差=结构 vs 黄线语义差（①）。

**已知边界（T2 对拍 2026-09-27，两场 demo）**：物理界外读数率 5~6%（hsv 11~17%）；
road_offset 相关 0.43~0.64、零相位滞后；帧间跳变在弯道局高于 hsv（行集组成抖动，
交 planner 0.8 新息门消化）；矮路缘石（<15cm）在 DA@336 场不可分辨——kerb 帧
读到的是人行道外缘（语义与旧 q20 的"人行道内缘"锚点不同，已记录于回归锁锚点注）。
时延：推理 ~20ms（折叠口径）+ 后处理 p50 ≈80ms，异步 worker 承载（150ms 窗）。

**geo_master 开关**（module config，"depth"|"hsv" 默认 depth）：road_offset 证据源
切换；黄线 `detect_boundary` 退役为骨架（照跑照记账、坏帧取证照旧，不再当证据源）。
弃权拍 road_offset=None → planner 退纯模型积分（一个 job 一个主人，不用黄线补位）。

**坑点**：
- `ego_mask.json` 上半身矩形皮肤相关（换车重算）；**车带下延段不需要换车重算**
  （真边界永不进中央列带的结构保证，见 commit 01b8fa5）。矩形盖不全的车身部分
  由动态自车吸收兜住（见上节①），矩形只需粗包络，不追车形。
- 权重缺失/推理异常 → observe 恒 None，深度层静默禁用（WARNING 一次），控制链
  不因感知停摆（与 perception 同一姿态）。
- 旧 q20 消费算法（全局逐行 q20 基线+固定相对门+双守卫）已被金标重考证伪，
  不得回退——过程与证据在 git 历史（ef5a42d~5f83a84 一代）与本区 README。
