## 1. 驾驶页锚点：齿轮图标的来历与它的漂移（本域实测）

通用采集纪律（半透明元素、裁剪、命名、坐标系换算）见主文档 §9.7；**本域的具体证据与数据
在此，主文档不复述**。

**第一版锚点是 HUD 上的"阶段"二字，实测不合格。** 它压在动态画布上半透明，像素逐帧与背景
混合——两种天光下跨帧匹配分 **0.94 → 0.71**，跌破阈值即失配。

**改用同区域的齿轮图标（不透明）**，当时读到跨帧 0.93，判为"稳定"。

**2026-09-16 两轮录制帧复核推翻了"稳定"这个结论**：

| 情形 | 锚点分数 |
|---|---|
| 驾驶途中（多数帧） | 0.93 ~ 0.99 |
| 驾驶途中（漂移段，**仍在驾驶**） | 缓降到 **0.80** 并成平台 |
| 真正离开驾驶页（画面切走） | **0.02** 量级（几乎归零） |

- 漂移的成因不是透明度，而是**彩色匹配（`colorspace: rgb`）把搜索区内的背景色一起算进
  相似度**——一例阴天灰底、一例晴天蓝底，齿轮本身没变形。改 `gray` 后 p50 由 0.919 升到
  0.970、漂移段 min 由 0.800 升到 0.843（有改善，但余量仍薄，不是根治）。
- **两端分离度极大**（0.02 对 0.80，约 40 倍），所以阈值取中间即可，两侧都能留足余量；
  节点当前取值见 `resources/pipeline/speedrush.json`。

**踩过的两个坑（都值得记）**：

1. **阈值不能用单天光、单轮样本标定。** 最初依据"跨帧 0.92~1.00，阈值 0.8 有余量"设了 0.8；
   实机出现 0.80 的驾驶帧后分数贴着线抖动，连续两次未命中被误判成"阶段结束"——流程随后去
   找奖励弹窗，而画面还在驾驶中，白等 20 秒后中止。**单轮样本的"稳定"是假象。**
2. **"半透明不行 → 换不透明图标"只解决了半个问题。** 背景会从"颜色"这一侧回到分数里；
   只换图标而不改匹配口径或标定方式，同一个病会再犯。

**兜底方向**（尚未实施）：多锚点 Or 组合（主文档 §9.7 已提），或直接读 HUD 上的 `阶段:N`
文字——那是**事实**而非推断，但它半透明，只能走 OCR，不能走模板匹配。

## 2. 驾驶阶段门控与循环节拍（本域）

- **驾驶页锚点节点的 `rate_limit` / `pre_delay` / `post_delay` / `timeout` 在图上显式置零或
  调小**：它是纯页面判定，不需要"每轮识别最低消耗"的地板，也不需要隐式等待；超时留短值让
  未命中时快速收尾。吃框架默认值的实测后果：主循环被压到约 1Hz（52 秒只录到 65 帧），
  且阶段结束要驻留 20 秒才记一次失配（容差要求两次 → 40 秒）。
- **流程步骤节点保留默认超时**：那些步骤本来就要等按钮出现，短超时会误判失败。
- 判据：就绪 = 连续命中若干次；离开对局 = 连续失配若干次（次数与间隔见 `module.py` 常量）。
- 循环退出时报一次实际节拍（轮数 / 秒数 / Hz）。**这是"采集能不能支撑训练"的第一手判据**，
  此前日志只有帧数没有速率，偏差看不出来。
- **2026-09-16 实机复测：两阶段各跑完整一段（未再出现途中误判）**，进入与离开的判定帧
  逐张翻图核对过——进入帧落在驾驶页（不是起步动画），离开帧分别落在奖励弹窗与回合结果页
  （不是过场动画中间）。阈值放宽到两端分离度的中间后，"贴着线抖动"这个病没有再犯。
  节拍与修复前的对照见日志的 `循环结束` 行（采集帧率受锚点复查的框架往返开销限制，
  不是采集侧也不是写盘侧；该开销尚未优化，方案里 30Hz 是控制期的目标）。

## 3. 演示数据录制（本域）

- 一个会话一个目录：`data/speedrush/demos/<时间戳>_p<阶段号>/`，含 `meta.json`、
  `frames.jsonl`、`pads.jsonl`、`frames/`；一局两个驾驶阶段各成一会话，便于按阶段筛。
  录制模式下还会多出 **`hud.jsonl` + `hud_meta.json`**（驾驶页 HUD 读数，见 §5）。
- **录制模式放宽两条启动约束**：不要求断开物理手柄（录制正要用物理手柄驾驶）、不需要手柄
  能力（录制期不创建虚拟设备，机器没装 ViGEmBus 也能录）。机制见主文档关于
  `ActivityModule` 启动约束的说明。
- 门控判定日志带 `frame=`，与 `frames.jsonl` 的 `frame_id` 对齐（日志墙钟只到秒，帧号才是
  可靠的共同坐标）。导出判定时刻的画面用
  `tools/experiments/speedrush_gating/export_gating_marks.py`。
- 帧文件名是**序号**（`000001.jpg` 起，`seq` 从 1 递增），不是帧号；`frame_id` 只在
  `frames.jsonl` 里，两者的桥是那份索引的 `file` 字段。

## 4. 节点的 ROI：按「单帧模板外扩」定，会在同一按钮的另一页失配（本域实测）

**症状**：实机跑到最后一页（段位分结算页）卡死——`点继续` 识别未命中，驻留重试
20 秒后本轮中止。

**根因**：`点继续` 一个节点服务两个页面（回合结果页／段位分结算页），两页的按钮位置
相差约 **18px**；而它的 ROI 是 `locate_templates.py` 按「模板每边外扩 15% 宽 / 25% 高」
**从单帧**算出来的，只剩 8px 余量——结算页整个落在搜索窗外。

用仓库自己的匹配内核在结算页截帧上复算（同一素材、同一尺度集）：

| 搜索范围 | 得分 | 说明 |
|---|---|---|
| 节点 ROI 内 | **0.568** | 低于阈值即失配——搜索窗把按钮切掉了 |
| 全图 | **0.888**（按钮真实位置） | 按钮就在画面里，只是比标定位置左了 18px |

**判据**：模板没坏、阈值没坏，坏的是**搜索窗**。`rect` 是「这个按钮**可能**出现在
哪里」，不是「它上次出现在哪」；一个节点服务多页时，ROI 必须覆盖各页位置的**并集**
再留余量。修法是把该节点的 rect 放宽到并集（当前取值见 `templates_roi.json`），
**不是**加模板、更不是降阈值——0.568 那个量级会放行大量误命中。

**顺带查出的第二件事：真源曾经不能由生成器复算。** `build_truth.py` 把节点一律写成
模块默认阈值，且不输出驾驶页锚点的 `rate_limit / pre_delay / post_delay / timeout`
——即 §1、§2 两处实测修复当时只活在「生成之后的手工编辑」里，跑一次生成器就会把它们
静默抹回默认值（阈值回到默认 → 漂移段误判复发；默认节拍 → 主循环回到约 1Hz，而这两处
都已由实机复测确认修好）。现改为由 `NODE_OVERRIDES` 表声明例外，并加回归锁
`tests/test_speedrush_truth.py`：断言「生成器输出 == 入库真源」。

**教训（与 §1 是同一条）**：单帧标定出来的「够用」是假象。阈值如此，ROI 也如此。

## 5. 驾驶页 HUD 实时读数（本域）

**是什么**：`hud.py` 的 `HudObserver` —— 驾驶途中在**独立低频线程**里取帧、按区域真源逐格
识别，把读数落成会话内的 `hud.jsonl`（每行一次采样）。它是"记分怎么来的"这类问题的
**唯一解仪器**：那些问题都卡在"没有连续序列"上，离线稀疏帧给不出（里程口径已由此定案，
其余待测项见 `RULES.md` §7）。

**为什么这样切**（改动前先读这三条）：

- **不碰 30Hz 驾驶循环**：单 ROI OCR 是 10~30ms 级，同步调用会把主循环拖慢一个量级。
  观察线程自带节拍（间隔见 `hud.SAMPLE_INTERVAL_S`），只做一次**非阻塞**取帧
  （`capture.frame_with_age()` 是 WGC 中心缓存的共享引用，多消费者各按自己节奏读是它的
  既有契约）；**首个样本推迟一个间隔**，阶段短于一个间隔时全程不碰 OCR。
- **行为与既有门控一致**：不创建虚拟手柄、不改驾驶循环节点的显式参数；观察线程与录制器
  **同一时机**启停（就绪后启、阶段结束的 finally 停），且**必须挂在录制会话上**——对齐
  目标就是同会话的 `frames.jsonl`，非录制模式既无会话目录也无帧索引可对。
- **通道序只走 `core.image_io`**：识别入口一律 RGB（`core.ocr` 对外收 RGB），本模块不写
  `[:, :, ::-1]`、不用 cv2 读图。

**已解问题与常驻判据**：里程口径（段累计 vs 滚动窗口）已由本仪器的连续序列定案为**约 10 秒的
窗口小结**（见 `RULES.md` §4.8），那条线索留下的常驻判据是 **`settled`（定值）**——卡片出现时
三行数字各自滚动爬升到定值，爬升段的值看着合理却只是动画中间帧。故卡片三格（`GATED_FIELDS`）
自 SCHEMA 2 起每格带 `settled`（= 与上一次可信采样同值、间隔 ≤ `hud.SETTLE_GAP_S`），
`hud_meta.json` 声明 `settled_fields` 与 `settle_gap_s`；消费方取 `trusted and settled` 即可，
**不要各自重算**（离线复盘工具读同一份，仅旧格式回退到同一规则）。它是**过去向**判据（写盘
流式、看不到未来），代价是每段平台的第一个采样点判不出定值；未定值**不改** `trusted`、也不进
`flags`——读对了就是读对了，判定与数据一起留下。

**记录必须可审计**（行里同时有原始与判定，而不是只有解析值）：每格记**原始文本**、
**解析值**、**是否过暗底闸门**（仅左侧面板三格）、**比分块按颜色判出的敌我归属**，以及
逐格 `trusted` / `settled` 与 `note`（理由清单）。面板缺席时识别会强行解码出小数字，只看数值
分不出"真读数"与"可信值"、更分不出"可信但还没涨到位"——审计要的就是这几层区分。`regions`
字段是区域集指纹，用于事后确认"这行是拿哪套框读的"。

**已知假读：标记而不是静默丢**（行照旧落盘）：

- `合计 < 里程` 必是假读——由公式「合计 = 里程 + 30×超车 ≥ 里程」自身导出（游戏事实见
  `RULES.md` §4.8）。落到行 `flags` 与该格 `note`。
- 单字面板读数与噪声不可区分；**只在可信读数必为多位的字段上标**（`overtake` 的合法域
  就是单字，不在内）——见 `hud.SINGLE_CHAR_SUSPECT_FIELDS` 的说明。**时间连续性是另一层
  判据**（`settled`），它与本层分开：这里是"读错了没有"，那里是"读对了但还没涨到位"。

**区域真源**：`resources/policy/hud_regions.json`（纯数据、无注释）。它自本模块落地起
**只此一份**：离线探针 `tools/experiments/speedrush_scoring/probe_hud_ocr.py` 的 `--rects`
缺省读它，NavKit Studio 的 speedrush HUD 只读面（`tools/navkit/studio_server.py`）也读它
——两份 rect 会各自漂移。`load_hud_regions()` 按 `check_truth.rect_checks()` 的同一口径
校验（4 元数值、[0,1]、`x1<x2`、`y1<y2`）并额外要求语义必需字段齐备，非法即 fail loud、
观察线程降级不启（记 WARNING，`_state.hud_recording` 为假，可查）。

**在场与敌我两条判据的出处**：`field_on_dark()` / `pair_sides()` 的口径搬自上面那个探针
（逐格复核立起来的），本模块是它们的运行期住户。**槽位不等于敌我**——两块比分面板会上下
互换，故 `score_a`/`score_b`（a=上档、b=下档）与 `rate_a`/`rate_b` 都只是**槽位名**，
敌我按块色成对判、单列在每格的 `side` 里；消费方按 `side` 取，不按槽位取。

**得分速度只为本方显示**（2026-09-17 实机三场确认）：本机侧 100% 有读数、对手侧只有零星
几处（那是背景假读）。故速度格只识别"本槽是蓝"的那一格，另一格**连 OCR 都不做**、
标 `not_displayed`；归属判不出时同样不读（标 `side_unknown`）——不知道这一槽是谁的，
就没有理由把那里的像素当读数。

**归属必须成对判**（`pair_sides`，2026-09-17 起）：两块面板必是一蓝（本机）一红（对手），
而面板是**半透明**的——背景景物会给两块染上同一偏色，**单块绝对阈值**在白天蓝天场会把两块
都判成"本机"（实测一场 62/69 行错，下游据此产出 51 处假"比分回落"：两家的值被混进同一条
序列）。故归属按**两块之差**定（公共偏色抵消），差小于 `SIDE_PAIR_MIN_DELTA` 两块都弃权；
条带采样同时收窄到**最饱和的一撮**（色条本身），让色条而非背景主导。单块形式 `block_side()`
只留给离线逐格标注（它**不是**权威判据）。逐格记 `side_source`（`pair`/`single`）留痕——
归属判错是这里最难事后归因的一类故障。

**坑点**：

- `seq` **按采样尝试递增**，缺口 = 缺帧或队列满丢样本（与 `frames.jsonl` 的 `seq` 同语义：
  缺口即证据）；计数进 `hud_meta.json` 与 `_state`。
- 反压照录制器：`put_nowait` 入队、队满丢样本计数，**绝不阻塞采样侧**。
- 引擎懒加载（`core.ocr` 唯一真源），失败降级返回 None、不抛；`hud_meta.json` 与录制器的
  `meta.json` 分文件，避免两个线程写同一文件。
- `timer` 是 `mm:ss` 倒计时，它的 `value` 按**秒**记（`parse_value`）；通用取整会把 `04:46`
  读成 4，看上去像"剩 4 秒"——读数对而解释错正是本记录要防的一类。其余格子取第一个整数。
