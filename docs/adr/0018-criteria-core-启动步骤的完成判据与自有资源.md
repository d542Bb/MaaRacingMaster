# ADR-0018（criteria-core）：启动步骤的完成判据与自有资源

## 背景

「启动游戏」此前的成功判据是**窗口出现**：拉进程 → 等窗口 → 把句柄交给连接层。ADR-0013 的证据节记的是「直启 39 秒登录完成进大厅、全程无人工登录、无弹窗」。

2026-11-05 的 1280×720 / 116 秒实录推翻了这条基线的普适性：窗口在 0 秒就出现，但游戏要到 1 分 51 秒才真正可用——中间有 76 秒的资源检查/合并（当天 130MB）/缓存清理/性能适配、一个必须确认的「引擎启动」登录页、以及约 15 秒的连续弹窗（每日福利 → 奖励结算 → 签到 → 营销弹窗）。模块在这 111 秒里连上去，就是对着加载页、登录页或弹窗盲点。

把「游戏准备好了没」留给每个下游模块各自猜，是这次改造要消掉的胶水耦合：启动步骤负责交付一个可用状态，下游从大厅起步。

## 决策

1. **完成判据改为「已知覆盖层清理后的大厅状态」**：至少一个大厅锚点命中、已知登录页完成确认、已知弹窗全部未命中，且该状态连续三轮确认（每轮约 1 秒）。**不保证**识别未知覆盖层；下游模块仍需自验操作前置条件——这是既有契约（各模块起跑节点识别自己所在页面），不是本方案代为承诺的事。

2. **启动链是启动步骤的自有资源，不是全局基础设施**：真源放 `maaracing_master/core/resources/startup/`，由 `LaunchGameStep` 显式加载。不放进 `core/resources/pipeline/`——那个目录会被所有模块的导航图按存在性自动并入，一条写错就拖着所有模块一起起不来。

3. **资源需求按本次配置声明，与业务结果分离**：`required_resources(config)` 只回答「要不要准备资源」；`wait_hall=false`（照旧完成）与 intent（跳过）都会得到空集，但结果不同，不能互相推导。

4. **执行态与模块运行态分离**：新增 `execution_active = _running or _step_active`，作为「能否真正睡眠」与「急停是否生效」的唯一判据；`_running` 保持「有模块在跑」的原义，`module_active` 与 GUI 运行显示不变。**这是一条独立的、影响全部内置步骤的行为变更**：从本版起「关闭游戏」这类步骤执行期间也能睡眠、也能被急停打断。

5. **资源所有权三层**：控制器拥有窗口连接、截图采集器、虚拟手柄**设备**与 ActivityContext；会话只独占导航图；手柄导航期间借的是**租约**（跑图结束即归还），归还租约不等于允许销毁设备——销毁由控制器按「谁创建谁负责」决定。

6. **收尾失败是独立状态**：框架 worker 未在期限内收摊时，一律不销毁可能仍被使用的原生对象，标记「会话污染」并拒绝下一轮启动。宁可泄漏一个进程周期的资源。

7. **错误传播靠独立通道**：MaaFW 协议里「识别命中但动作失败」进入该节点的 `on_error`，与「视觉没命中」同路。因此 `on_error` 只承担视觉未命中与可重试的动作失败（前台守卫、导航超时）；基础设施故障（手柄未绑定、截图帧龄超限、取不到帧尺寸、桥内未捕获异常）走 `report_fatal()`，由轮询每轮检查、并在 job 结束后**再检查一次**，且不被 job 的成功状态覆盖。

## 后果

**收益**：

- 启动步骤交付一个明确的后置条件，下游模块不必各自处理加载页、登录页与启动弹窗。
- 启动链写错只影响启动步骤；普通模块的加载路径与模板搜索根完全不变。
- 收尾超限不再以崩溃收场（0xC0000005），失败原因可读、下一轮被明确拦住。

**代价与约束**：

- 登录页/弹窗 UI 一改版，整轮队列会因超时中止；逃生开关是关掉「进入大厅」。
- 「已知覆盖层已清」不是「绝对干净」：未知弹窗仍可能漏判，靠下游模块自己的识别闸门兜底。
- 启动步骤执行期会真正睡眠、也响应急停——这条不随 `wait_hall` 回退。
- 前台（鼠标）模式下连接会抢前台并把窗口改成 720p；这是模块启动的既有行为，但第一次「只跑启动步骤」的用户会感知到。
- `fatal` 有一帧级的残余窗口：故障在自定义动作内部记录时，框架可能已按 `on_error` 跳一次；所有节点的 `on_error` 都指向汇聚节点（动作为 `DoNothing`），最多多跑一轮空识别。

**被否方案**：

- **启动链放进 `core/resources/pipeline/`**：看似「共用」，实际把启动专用的节点与模板变成所有模块的全局依赖，且模板目录会进入所有模块的首搜路径。
- **用类属性声明资源需求**：控制器看不到本次配置，`wait_hall=false` 时仍会建连接、开采集，与「关闭即回旧行为」的承诺直接矛盾。
- **用 `pipeline_override` 在运行时改登录动作**：真源与运行行为分叉，`truth` 看不见，且两种点击方式下图上都是错的。
- **把 `execution_active` 塞进大厅功能的回滚承诺**：它影响全部内置步骤，属于独立决策。
- **用固定坐标点登录按钮**：违反「目标坐标来自识别框」的既有定案，且登录页布局随版本漂移。

## 证据

- **实证（录像，2026-11-05，1280×720 / 116s）**：0:00 出窗口；0:02–1:18 资源检查/合并/清理/适配；1:21 登录页（右侧功能图标列 + 「引擎启动」）；1:29 确认；1:35 大厅 UI；1:36–1:50 连续弹窗；1:51 干净大厅。ADR-0013 的「39s 无人工登录」是缓存全热的最好情况。
- **匹配器行为实测**（本仓 `template_match`，7 档多尺度 `TM_CCOEFF_NORMED`）：同一帧亮度 ×0.5 后大厅锚点分数仍为 1.000；高斯 3px 降至 0.741/0.758，7px 降至 0.647/0.640。→ 压暗不能作为「非大厅」的判据，只有模糊 + 阈值可以；大厅锚点阈值因此取 0.90（干净帧 0.989/0.994，弹窗帧最高 0.826）。
- **一手协议**：MaaFramework `docs/zh_cn/3.1-任务流水线协议.md` 第 42–44 行（动作失败 → `on_error`）；`MAAFW_GUIDE §5.2`（入口节点识别自己不命中则任务失败）、§7.1（worker 活动时销毁 C 句柄必崩 `0xC0000005`）。
- **机检**：`python tools/pipeline/truth.py`（34 节点、0 error 0 warn）；`tests/test_startup_truth.py`（真源形态与排序）；`tests/test_startup_confirm_window.py`（确认窗口内弹窗优先、清理后重新计数）；`tests/test_builtin_launch_hall.py`（三条路径）；`tests/test_controller_step_link.py`（执行态与资源所有权）；`tests/test_nav_graph_fatal.py`（fatal 收尾复查与时限）；`tests/test_nav_graph_teardown.py`（收尾失败态不销毁）。
