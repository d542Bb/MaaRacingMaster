## 背景

GUI 要同时成立三件事：**HTML 前端**（复用 Web 技术，且离线可用）、**原生窗口行为**（DWM 动画、系统 caption buttons、Snap）、**可用的窗口拖动区**。四候选（Tauri v2 / WPF `WindowChrome` / `FormBorderStyle.None` 类 / WinUI 3）经实测比较。

约束的物理来源：**WebView2 是独立 HWND 且铺满客户区**——任何在客户区内模拟标题栏的方案都会被它遮挡并吞掉鼠标；而 `FormBorderStyle.None` 类方案没有 `WS_CAPTION`，拿不到 DWM 动画。

## 决策

**正式 GUI = `apps/MaaRacingMaster.Shell/`（WinUI 3 shell + WebView2 HTML 前端）+ `core/sidecar.py`（Python 业务后端，JSONL RPC）。**

**硬约束（不得回退）**：同时拿到 HTML 前端、原生窗口行为与可用拖动区，只有 `AppWindowTitleBar` 的**系统级 NC 处理**能做到——不得回退到 WPF `WindowChrome` 或 `FormBorderStyle.None` 类方案。

副作用契约：shell 只做**窗口、启停 sidecar、转发消息**三件事，业务一律不进 C#；sidecar transport 契约与坑点见其 README。

## 后果

**收益**：
- 三件事同时成立：HTML 前端离线可用、系统 caption buttons 与 DWM 动画保留、`SetDragRectangles` 给出可用拖动区；
- 壳与业务解耦：换前端不动 C#，换 GUI 不动 Python 业务（Python 是唯一业务后端）。

**代价与约束**：
- **drag region 必须挖孔**：顶部整条设为 drag rect 时，双击 tab / 品牌按钮区会触发最大化（被「标题栏」行为吃掉）——需前端测量交互矩形回传，C# 按 DPI 换算挖孔；窗口尺寸变化须重设（物理像素）；
- 系统 Snap Layout hover 在 `AppWindowTitleBar` 下不出现（疑似系统 SnapAssist 设置，未深究）；
- 拖动区、标题栏高度等窗口行为只能经 `AppWindowTitleBar` 调整，**不能绕回客户区内自绘**。

**被否方案**：
- **Tauri v2**——Windows 无 Overlay 实现；
- **WPF `WindowChrome`**——WebView2 airspace 遮挡客户区，吞掉鼠标；
- **`FormBorderStyle.None` 类**——无 `WS_CAPTION`，拿不到 DWM 动画。
