# ADR-0011：性能数据由 core 单一采集、判级、落盘，模块只能声明行

- **状态**：`accepted`
- **日期**：2026-10-28
- **决策者**：用户拍板（"应该也成立一套契约吧……反向约束 plugin 给的信息规范化"），AI 落实施
- **相关**：commit `dc52f2d`（契约与通用渲染）、`59e6de9`（统一采样与落盘）、`789fade`（线程段）、`0c5a1da`（计时精度修复）· [core/CODE_WIKI.md §1.14–1.16](../../maaracing_master/core/CODE_WIKI.md) · [ADR-0010](0010-记录流分类与玩法流水汇.md)（perf.jsonl 的流分类）

## 背景

性能卡此前是**每个模块各写一套**：竞速一套、鉴宝一套、未登记模块回退到最早那套（数值还写死 `--`）。三套模板并存，数据面是模块返回的自由字典——模块自己定 `ok/warn/error`、自己拼单位与文案、自己决定状态文本长什么样。

由此产生的不是"代码不好看"，是三个可验证的失真：

1. **判级口径无法统一**：同一档"偏高"在两个模块里含义不同，core 无法复核，也无法聚合出整卡健康度。
2. **面板与日志不是同一份数据**：模块读数只活在内存里给面板看，`perf.jsonl` 只有系统资源——卡顿发生后查不到当时的拍率与决策状态。
3. **前端必须认识模块**：新增模块 = 改前端模板，否则落到那套写死 `--` 的回退卡上。

同时真机实测确认了一个反向风险：现成的线程采集库（psutil）单轮 60–90ms 且不释放 GIL，按秒采集会把 60Hz 的控制循环冻出 90ms 空档——**监控本身可能成为被测对象的故障源**。

## 决策

**性能数据只有一个采集者、一个判级者、一个写手，模块只能声明"自己报哪几行"。**

四条具体规则：

1. **模块在类上声明行**（`PERF_CONTRACT` / `PERF_ROWS` / `THREAD_LABELS`），行只能落在 core 定义的闭集里：`kind` 五值锁死单位与合法域，`category` 两档，`stat` 两值且只对 `rate`。模块**不自带单位字符串、不自判等级、不提供卡片模板**。
2. **判级权二分**：数值类的 `ok/warn/error` 由 core 按声明阈值算；状态类的等级由模块给（业务语义阈值表达不了），但状态**不参与跨模块健康聚合**。
3. **单一时钟、单写手**：采样器是唯一的采集 tick 与 `perf.jsonl` 的唯一写手；面板读采样器快照，不再直连模块。同一会话内不存在第二个产生点。
4. **违规只降级**：声明不合规整行拒绝、运行时值非法只让那行失效（显示「—」+ 原因），不崩、不显示假值、不静默。

强制力分三层：声明期校验（加载时整行拒绝）、运行期校验（五道闸 + 逐行隔离）、**开发期校验器**（模块自己的测试 import `validate_rows`，不合规在提交前就红）。

## 后果

**收益**：

- 新增模块零前端改动：声明几行就有卡片，模板不再按模块分支。
- 面板与日志同源：看到的和记下的是同一条样本，事后能回答"卡的那几秒拍率多少、决策在干什么"。
- 判级口径统一到一处，整卡健康度可聚合（取所有行最差一档）。
- 监控自身的开销与故障可见：取值超 5ms 告警、写盘失败记缺口、采样停摆由外部观察者报出。

**代价与约束**（后续开发者会因此做不了什么）：

- **插件作者不能自定义指标形态**。想要 core 不认识的行（新 `kind`、新单位、新展示形态）必须回头改 core 闭集，不能就地扩展。这是刻意的：闭集换来前端、单位换算、统计全部自动。
- **不能自定"什么算异常"**。阈值写在声明里由 core 执行；判级散回模块等于取消统一口径。
- **core 侧不能有第二个采样时钟或第二个 `perf.jsonl` 写手**。需要更高频率就调采样周期，不能旁路加一个。
- **模块取值口必须是纯读、常数时间、不抛异常**。契约**不承诺**能从中恢复：同步调用卡住就是卡住，core 只保证"断档可见"，不保证"能解卡"。
- **面板数字最多滞后一个采样周期**（1s）。换的是"看到的＝记下的"。
- **模块指标不可跨模块比较**。即使 `stat` 相同，窗口由模块自定、阈值按模块标定；跨模块比较须先另立窗口契约。
- 行数上限 player 3 / diagnostic 8——卡片不是调试面板，事件型、要毫秒精度的诊断走模块自己的流水。

**被否方案**：

| 方案 | 否决理由 |
|---|---|
| 保持模块自定义字典透传 | 判级、单位、文案各写一套；前端必须认识模块；日志无法带领域数据 |
| 每模块一套卡片模板（原状） | N 个模块 N 套模板，新模块必须改前端；同一形态在模板里重复三份 |
| 面板直连模块（原 4Hz 轮询） | 看到的和记下的不是同一份数据；且 4Hz 打模块取值口，成本高一个量级 |
| core 统一滑窗算拍率 | 现有口径是"拍间隔中位数的倒数"，换成滑窗平均会改变语义，阈值按老口径标定 → 告警时刻平移 |
| 声明期强制模块必须报性能行 | 逼模块为填满而编指标，比空着糟；没声明就只显示资源面 + 启动记一条 INFO |
| 采样超时保护（同步调用加超时） | `Future.result(timeout)` 只是不等待，不停止被调方；承诺了做不到的能力比不承诺更危险 |

## 证据

- 一手核查：`maaracing_master/core/perf_contract.py`（声明期 `validate_rows` / 运行期 `normalize`，纯函数无状态）、`base.ActivityModule` 的三个空默认声明属性、`perf_sampler.set_domain_reader` / `set_thread_labels`、`sidecar.get_status` 只读快照。
- 机检：`tests/test_perf_contract.py`（26 例：key 正则、label 四步含截断后复核、阈值成对、五道闸、逐行隔离、状态文本五步、不判级仍校验）、`tests/test_perf_sampler_domain.py`（16 例：领域面入样本与落盘、单写手静态断言、写盘缺口三拍恢复、断档可见）、`tests/test_thread_probe.py`（11 例：三条过滤、身份复用、负差分降级、标签兑现）。
- 实证：真机会话 `20261028_210926_1`（144 样本）——拍率稳定 19.8 次/秒、线程段每拍有值、零性能告警；同局暴露计时精度缺陷（`monotonic` 15.6ms 台阶）已修并加回归锁。
- 反证：同局进程占用 525% 而 Python 线程合计 189%，未归因 335% 落在 onnxruntime 推理线程池——**本决策不解决原生线程不可见**，那部分只体现为"未归因占用"，见 [core/CODE_WIKI.md §1.16](../../maaracing_master/core/CODE_WIKI.md)「已知盲区」。
